第一部分 · 项目概述

1. 项目背景

1.1 一句话定位

面向保租房/新居住场景的本地生活服务中台：以"房源"为入口，聚合家政、保洁、维修、搬家、保姆等生活服务，连接服务商（B）、服务者（S）、租客（C）、平台运营方（P）与金融机构（F），实现服务全流程的标准化、可监管、可结算。

1.2 要解决的痛点

痛点 现状 平台解法
服务不标准 家政服务无统一工序、价格、等级 平台定义 SPU 标准品（标准工序/参考价/最低等级）
服务者不可信 无资质认证、无责任险、无评价体系 七段链准入 + 责任险强制投保 + 信用引擎
交易不透明 定价混乱、抽佣随意、账期不清 分级抽佣矩阵 + 银行托管 + T+1 划付
监管缺抓手 住建/监管部门无数据入口 G 端白名单 + 评级公示 + 数据中台
垄断风险 头部运营商一家独大 运营商市占率 ≤30% 防垄断红线

1.3 产品目标（北极星）

指标 目标
北极星 月完结服务单量（目标：月 1.2 万单 → 3 万单）
次北极星 订单完结率 ≥ 95%；服务者 30 天复购占比 ≥ 40%
质量 客评均分 ≥ 4.5；投诉率 ≤ 2%
效率 派单主策略命中率 ≥ 78%；L0 准入闭环 < 1 天
合规 责任险投保率 100%（接单前置）；白名单覆盖率 100%

1.4 产品范围（版本边界）

版本 范围 交付要点
V1.0（本期） 新居住频道 + 家政服务闭环 类目/SPU/产品/服务者/订单/支付/评价 + 管理台 + 商家对接 API + 微信小程序 URL Link 跳转
V1.5（规划） 服务商生态 服务商入驻/白名单/LV 评级、培训认证、责任险、信用引擎
V2.0（规划） 监管与金融 G 端监管、银行托管分账、API 网关开放、Webhook 事件订阅、数据中台

第二部分 · 用户与角色

2. 用户角色总览

2.1 角色矩阵

角色 代号 说明 核心诉求
租客/客户 C 下单购买生活服务 找得到、信得过、付得清
服务商（商家） B 人力服务商/运营商，上架产品、接单派工 好上架、多接单、快结算
服务者 S 保洁/维修/搬家等一线人员 多派单、高收入、有保障
平台运营方 P 平台管理、准入审核、派单规则、结算 管得住、看得清、算得准
金融机构 F 银行托管、分账划付 资金安全、对账清晰
监管部门 G 住建厅等 白名单、公示、数据监管

2.2 权限边界（要点）

  • P 端：管理全部平台数据，但 PII（个人隐私）仅 DPO 可读写，平台运营无权限
  • B 端：仅操作本机构产品/订单，不可改 SPU 标准工序
  • S 端：仅操作本人接单/履约/评价
  • G 端：白名单审定、评级公示、监管查询（只读为主）

4. 基础数据模块（P 端）

4.1 服务子类目管理

入口： 控制台 → 服务子类目管理

  • 一级类目：保洁 / 维修 / 搬家 / 保姆 / 家政
  • 子类目支持：名称、图标、排序、启用状态、类型标签（如 renli 人力）
  • 类目停用后：C 端不可见、商家不可新建产品、存量产品不可售

4.2 服务标准品 SPU（平台核心资产）

入口： 控制台 → 服务标准品 SPU

  • SPU = 平台定义的标准服务：标准工序、参考价（价格区间）、所需最低服务等级、规格
  • SPU 标准工序商家不可修改（商家只能基于 SPU 创建自己的产品并定价）
  • SPU 停用/删除时校验：存在上架产品则禁止删除
  • 平台规则：SKU = SPU + 服务者 + 价格——同一 SPU 挂不同商家即形成比价

4.3 等级与技能矩阵（L0–L7）

入口： 控制台 → 等级与技能矩阵

等级 定位 说明
L0 入门 建档可接简单单
L1 基础 常规服务
L2 熟练 基线派单权重 ×1.0
L3 资深 权重 ×2.0，可带徒
L4 专家 权重 ×2.5，复杂工单
L5+ 经营/培训/标准 独立结算轨道，非交易主体
  • 等级支持版本管理：新建版本 → 灰度 → 发布，发布后影响派单权重与分账
  • 晋级条件：在岗时长、完结单量、客评、学时、综合考、复杂工单、信用分

4.4 题库与试卷

入口： 控制台 → 题库与试卷

  • 题目覆盖 6 类核心岗位 + 6 类延伸岗位，题型：单选/多选/判断/情景实操
  • 试卷模板与 L0–L7 等级口径对齐
  • 质量告警：高错率题目（>80%）、低区分度题目触发改版

4.5 履约保障与责任险

入口： 控制台 → 公共底座 → 履约保障与责任险

保障产品 覆盖 保额
服务者责任险 人身/第三者财物/纠纷 最高 ¥50 万/次
履约保证金 爽约/违规先行赔付 ¥2,000 起
客房安心险 家电家具损坏 最高 ¥10 万
家财险 房源端财产保障 最高 ¥10 万
  • 必投保才可接单（硬门槛）；保费 ¥18/月平台统一议价，信用分 >4.5 享 8 折
  • 理赔结果回流信用引擎

4.6 信用规则引擎

入口： 控制台 → 信用规则引擎

  • 42 条规则：加分 18 / 扣分 14 / 阈值告警 6 / 冻结解冻 4
  • 典型规则：五星好评 +1.5、月度全勤 +5.0、复杂工单 +3.5、投诉受理 −4.0、退单偏高 −2.4
  • 评价→信用分联动（V1.0 已实现）：5 星 +2.4 / 4 星 +1.2 / 2-3 星 −1.5 / 1 星 −3.0
  • 规则模拟器 + 灰度发布（CANARY）+ 漂移检测

5. 服务商准入模块（B 端）

5.1 入驻申请受理（V1.0 已实现雏形）

  • 商家（vendor）建档：类型（人力服务商等）、名称、联系方式、状态
  • 平台分配 vendor_id + HMAC 密钥（对接 API 用）
  • 受理 SLA 建议 < 1 天

5.2 产品（SKU）管理（V1.0 已实现）

B 端能力（管理台 + 开放 API 双通道）：

功能 说明
产品列表 按状态/类型筛选
创建产品 选 SPU + 定价 + 规格 + 库存
编辑产品 改价格/库存/名称
状态变更 上架 on / 下架 off / 售罄 soldout
删除 软删

约束： 商家不能修改 SPU 的标准工序；产品必须挂在一个平台 SPU 下。

5.3 排班档期（V1.0 已实现）

  • 商家按产品 + 服务者 + 日期时段生成档期（批量生成）
  • 档期容量：默认 1（一个档期一个服务者）
  • 滚动排期：平台自动补足未来 5 天档期，保证 C 端随时可约
  • 档期状态：open（可约）/ closed（关闭）
  • 占位规则：下单记录意向（软校验），支付时才占用名额，避免弃单泄漏档期

5.4 B 白名单与 LV 评级（V1.5 规划）

  • LV1 单城（1000 套以下）/ LV2 跨市（5000 套以下）/ LV3 省级（5000 套以上）
  • 双审制流程 ~45 天：受理 → 资质初审 → 财务尽调 → 合规终审（住建厅）→ LV 评级 → 公示上链
  • 防垄断红线：任何运营商市占率 ≤30%；持有方可同时委托 ≥2 家运营商

5.5 M 物资品类认证 / T 培训机构认证（V1.5+ 规划）

  • M：6 品类认证（家具/家电/建材/智能锁/涂料/卫浴），6 步流程 ~60 天
  • T：培训机构 LV1–3 分级认证，课程认证、考务、结业学时闭环

6. 服务者准入模块（S 端）

6.1 七段链准入（V1.5 规划）

入驻受理 → 培训认证 → 考务考试 → 结业学时 → 发证上链 → 投保 → 白名单
  • 实名核验：身份证 + 人脸 + 人社职业资格库比对
  • 白名单是接单的最终开关：P 端发证后仍需 G 端白名单通过
  • 证书：有效期 24 个月，到期前 60 天续期窗口，吊销需审批流

6.2 V1.0 已实现的服务者能力

  • 服务者建档（姓名/等级/头像/所属商家）
  • 在线状态管理（C 端只展示在线服务者）
  • 自动派单轮询（无首选服务者时按顺序分配）
  • 客户指定服务者优先（from_customer 标记）

7. 派单监控模块

7.1 派单规则（V1.0 简化版已实现）

当前实现（真实逻辑）：

① 客户下单时指定服务者 → 派单时优先尊重（from_customer = true）
② 未指定 → 按在线服务者轮询分配
③ 派单前置条件：订单已支付 + 状态为 pending

规划（V1.5，流量倾斜策略）：

策略 内容
分级流量权重 L4 ×2.5 / L3 ×2.0 / L2 ×1.0 / L1 ×0.8
新人扶持池 L2→L3 后 14 天 +30% 派单机会
客户复购绑定 30 天内指定原服务者
距离硬约束 ≥5km 不派单
投诉冷静期 中优以上投诉处置中隔离 24h
区域反垄断 单点驻店 90 天强制轮岗

7.2 订单概览（V1.0 已实现）

  • 订单漏斗：待派 → 已派 → 已接 → 服务中 → 待评价 → 已评价
  • 全量订单查询：按状态/支付状态/手机号筛选
  • 订单统计：各状态计数（stats 接口）

7.3 订单状态机（V1.0 已实现）

pending → dispatched → accepted → serving → done → rated
    └──────── cancelled
状态 说明 触发方
pending 待派单（已支付） 客户下单
dispatched 已派单 平台/自动
accepted 已接单 服务者
serving 服务中 服务者
done 待评价 服务者完成

7.4 维修报价（V1.0 已实现）

  • 仅维修类目支持：服务者上门后按实际项目报价（quote_items）
  • 报价金额累加进订单费用，报价说明追加订单备注

  • 事件目录 24 类（CloudEvents v1.0）：cert.issued / level.changed / credit.score.updated / order.completed / complaint.created / exam.passed / material.batch.qc-*

9.6 通知中心（V1.5 规划）

86 个消息模板，多通道（短信/App push/微信/站内信/邮件/12345 回写），送达率 99.4%。

第四部分 · 平台核心规则

10. 必须坚守的业务规则

规则 1：SKU = SPU + 服务者 + 价格

  • 平台定义 SPU（标准工序/参考价/最低等级）
  • 商家基于 SPU 创建产品（SKU），可自定义价格与库存
  • SPU 标准工序商家不可修改
  • C 端同一 SPU 可多商家比价

规则 2：运营商市占率 ≤30%（防垄断红线）

  • 任何运营商（含贝壳省心租）市占率不超过 30%
  • 持有方可同时委托 ≥2 家运营商
  • 集采底价与流量分配对全部白名单运营商同业并列
  • 公平竞争审查每年 1 次，3 年中评 + 5 年回看

规则 3：无责任险不接单

  • 责任险投保是服务者接单的硬门槛（投保率目标 100%）
  • 理赔结果回流信用引擎

规则 4：支付才占档期

  • 下单仅记录档期意向，不占名额
  • 支付时占用：档期已满/已关 → 支付失败（409），用户改期
  • 避免弃单/未支付订单永久泄漏档期座位

规则 5：管理台写接口必须鉴权

  • /api/juzhu/jz/* 的 POST/PUT/DELETE 与 admin 接口一律要求 API Key
  • 商家侧接口一律 HMAC-SHA256 签名 + 时间戳防重放（5 分钟窗口）

规则 6：信用分联动评价

  • 评价直接驱动信用分（5 星 +2.4 / 4 星 +1.2 / 2-3 星 −1.5 / 1 星 −3.0）
  • 信用分影响派单权重与保费

第五部分 · 非功能需求

11. 非功能需求

11.1 性能

指标 要求
API P95 延迟 ≤ 200ms（平台接口）/ ≤ 24ms（网关规划）
接口成功率 ≥ 99.4%
C 端页面首屏 ≤ 2s
订单列表 单次查询 ≤ 200 条（limit 上限）

11.2 安全

  • API 鉴权双轨：API Key（管理台）+ HMAC-SHA256（商家）
  • 签名时间戳 5 分钟防重放窗口
  • CORS 全局放开（当前实现），生产环境建议收紧为白名单域名
  • PII 数据脱敏分级，仅 DPO 可读写（规划）
  • 金额整数传输（分），杜绝浮点误差

11.3 可用性

  • 服务端 SQLite 单机部署（当前），建议 V1.5 起评估主从/备份策略
  • 订单日志全链路留痕（log_json），支持审计追溯
  • 档期数据一致性：支付占用原子操作，并发下不超卖

11.4 兼容性

  • 前端支持移动端 H5 与微信小程序跳转（URL Link）
  • 商家对接：Python 参考实现提供 HMAC 签名库

12. 验收标准

模块 验收点
类目/SPU 增删改查；SPU 标准工序商家不可改；删除校验

档期 批量生成/单条/关闭；滚动 5 天；支付占位不超卖
订单 创建→支付→派单→推进→评价全闭环；日志留痕
评价 1-5 星校验；信用分联动正确
维修报价 仅维修类目可报价；金额累加正确
微信跳转 URL Link 生成；GR 订单创建；回调闭环
回调 paid/assigned/serving/completed/cancelled 全状态；签名校验
鉴权 管理台接口无 Key 返回 401；签名错误返回 401

12.2 灰度策略

  • 单城市试点（沈阳）→ 验证订单漏斗与服务质量 → 多城市复制
  • 派单规则调整先 A/B 实验（如 L5 权重 ×3 vs ×2.5）再全量
  • 信用规则上线走模拟器预演 + CANARY 5% 灰度

12.3 监控指标

  • 订单漏斗各环节转化率（待派→已派→已接→服务中→完成）
  • 档期利用率、支付转化率、弃单率
  • 接口错误率、P95 延迟
  • 评价分布、投诉率、信用分分布
