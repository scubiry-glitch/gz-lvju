1短租按晚定价

户型级夜价 新增生效

「我们目前的业务是短租，每晚价格独立（周末涨价、节假日溢价、平日低价）；接口中的 price_from 是按月租金折算，这样不太好。」
怎么改的

units.price_night（元/晚）此前在 rental 频道收得下但不参与计价， 现在两个频道一致生效。默认夜价取值顺序：

顺序取值说明
1units.price_night本次生效：你们直接传每晚价
2rent_monthly ÷ 30保留，老数据不受影响
3price_from ÷ 30保留，兜底
最高房态日历逐晚覆盖价不变：周末 / 节假日分档仍走这里
你们要改什么：不用改。继续传 price_night 即可生效； 存量按 rent_monthly 传的房源价格一分不变。

2起价改为选填 + 卡片展示价

price_from 选填 门槛调整

「房源 project 上的 price_from 是否可以非必填？我们目前没有 project，属于对接适配，会构造一个出来；价格设定在 unit 层级，不想使用 price_from。」
怎么改的
  • price_from 改为选填，不传即可。
  • 上架门槛从「必须有起价」换成「每个户型都能算出一个大于 0 的默认夜价」—— 不传起价时，每个户型自己带价（price_night 或 rent_monthly）就行； 传了起价，全部户型自动继承，行为与旧闸一致。缺价会 400 并点名是哪个户型。
  • 新增只读出参 price_from_display / price_unit / price_note， C 端卡片价格由平台算好下发。
  • 顺带堵了个洞：算不出价的订单现在直接拒单（400），不再 0 元成单。
卡片展示单位怎么定（A″ 口径）
房源单位取值
minsu 民宿night 按晚起价（price_from 本就是元/晚）
rental 且带「旅居」tagnight 按晚最低可售单夜价（见下）
其余 rental（保租房 / 长租）month 按月起价语义，展示不变

「最低可售单夜价」怎么算：从今天起按自然月向后扫描（最多 12 个月，与 C 端可订窗口同口径）， 取第一个存在可售间夜的月份，该月内最低单夜价即展示价；扫满仍无可售 → 卡片显示「暂无可订」。 没有房态记录的晚 = 默认可订（按默认夜价），不会误判成无房。

你们要改什么：不用改。不想传起价就不传；想控制 C 端「¥X 起」，继续传即可。
一处与你们原始描述的差异，请确认：你们写的是「图集最少 7 张」， 而平台原上架门槛是合计 ≥ 8 张（房源图 + 户型图）。已按你们的 7 张调整：现在合计 ≥ 7 张 + 至少 1 张封面即可上架（见第 4 条）。

3多渠道库存：净可售 + 默认关房

净可售 available_qty 新增

「户型的 total_qty=6，贝壳侧卖了 2 个，橙途其他渠道卖了 1 个，还有 1 个暂不可售（未保洁）→ 可售库存 6−2−1−1=2。 房源经营为多渠道、且有部分库存暂时不可售，可售库存会不断变化。」
怎么改的

新增 available_qty（净可售）：直接推「这一晚平台还能卖几间」，按你们自己的口径算。 平台记下推送时点的已订数作为基线，之后只有平台自己卖掉的才从这个数里扣，取消自动加回； 并以「物理余量（total_qty − 已订）」封顶，防对账漏项导致超售。

动作平台剩余说明
推 available_qty: 2（此时平台已订 2）2基线记 2；旧口径会二次扣成 0
平台又卖掉 1 间1只扣平台之后的占用
客户取消2自动加回，不越过推送值
他渠道再卖 1 → 重推 available_qty: 11基线刷新为当时已订数

qty（放出总量，含平台已订）与 available_qty 同一次调用只能传一个（同时传 400）。 写 qty 会把基线清空，回到旧语义。推送响应会逐日回 days[]（qty / booked_qty / remaining）， 推完即可对账，不必再查一次日历。

防超售兜底：推的数若超过实际剩下的房间数，平台按物理余量封顶。 所以推大不会超售，推小才会少卖——对账宁可略保守。

默认关房 default_closed 可选开关

净可售解决「推过的晚怎么算」，默认关房解决「没推过的晚怎么办」。 平台默认「没推过的晚 = 可订、放出 = total_qty」——对多渠道商家这很危险： 你们在别处卖掉、或临时不可售的晚，只要没推过，平台照样放出去卖。

把房型的 default_closed 设为 true 后：只有你们显式推送过放出量的晚才可订； 没推过的晚、只设过夜价没设放出量的晚一律不可订。缺省关闭（不配置 = 现状）， 只作用于指定户型的预订，整栋单语义不变。

你们要改什么：不用改。不用净可售也可以继续用 qty； 默认关房是可选开关，建议需要多渠道对账的房型开启，并按未来 12 个月滚动推送放出量。

4图集全量覆盖（换图 / 撤图）

photos/sync 新增接口

「只提供了新增图片的功能。反复迭代房型图片（换实拍图、替换旧图、撤掉失效图），每次只能 add； 图片越堆越多，图集冗余、C 端展示杂乱。」
怎么改的

新增 photos/sync：把该实体当前完整的图集传上来，平台对比存量—— 保留列表内的（原地更新，图片 id 不变、C 端引用不抖）、移除不在列表内的，整体一个事务。

{ "project_id": 1611, "unit_id": 3101,   // 不传 unit_id = 房源级图集
  "photos": [
    { "url": "https://cdn.example.com/p1.jpg", "category": "bedroom", "sort": 0, "is_cover": true,
      "external_id": "IMG-1001" },   // 你们侧的稳定图 id
    { "url": "https://cdn.example.com/p2.jpg", "category": "living", "sort": 1,
      "width": 1920, "height": 1080 }        // 声明值可选
  ] }
→ 200 { "applied": 8, "added": 5, "updated": 3, "removed": 2,
        "cover": "…/p1.jpg", "truncated": false, "warnings": [],
        "photos": [ /* 覆盖后的完整图集 */ ] }
你们关心的几个点
事项处理
同一张图怎么认匹配键 external_id 优先、URL 兜底。你们说 URL 带签名会变——带上稳定图 id 即可， 换签名 URL 也只是原地更新那一张。
图片分类category：bedroom 卧室 / kitchen 厨房 / bathroom 卫生间 / living 客厅 / nearby 周边 / other 其他（可选，缺省 other）。 C 端详情图集滑动时会显示分类。
展示顺序sort 从小到大，平台归一化为 0..n-1 落库；不传按数组顺序。
数量单次上限 100 张，超出按 sort 截取前 100 并回 truncated: true + warnings（不静默丢图）。
大小 / 分辨率单图 ≤10MB、分辨率 ≥800×600。推送时可带 width/height/size_bytes 声明值即时校验（零网络开销）；上架时平台抽检封面 + 靠前 2 张 真拉取核对。
抽检会不会卡上架确定性不合格（超 10MB / 小于 800×600 / 非图）→ 400 拒绝； 仅网络不可达（超时 / DNS / 非 200）→ 放行并回 warnings，CDN 抖动不卡上架。
老的 photos/add保留，且改为幂等：同 URL / 同 external_id 重推 = 原地更新， 不再堆重复行；顺带修掉「传了 sort_order 却被忽略」的问题。
图集张数已按你们的 7 张对齐： ① 上架门槛 = 房源图 + 户型图合计 ≥ 7 张且至少 1 张封面（原为 8 张，已下调）；
② photos/sync 不卡下限（只卡 100 张上限）——「≥7 张」是上架闸，不是每次覆盖的闸， 这样多户型房源才能先建后补。覆盖后不足 7 张时响应里会给一条 warning 提示。

5住宿规则归位到户型

最短连住下放户型 口径调整

「projects 上的 min_stay_nights 和 units 的 cancel_policy，建议调整到一个实体中。 可以考虑把 projects 的 min_stay_nights 也调整到 unit 层级。」
怎么改的

最短连住现在户型级可配，生效顺序 户型 > 房源 > 频道默认（rental / minsu 默认均 15 晚）。 取消政策本来就挂在户型上——这样两条住宿规则都可以只在户型上配，不用再记哪个在房源、哪个在户型。

  • 写入：units/create / units/update 传 min_stay_nights（rental 1–365 / minsu 15–365，越界 400）。
  • 房源级 ext.min_stay_nights 保留，语义降级为「房源默认值」。
  • 整栋单（不指定户型）按排序最前的户型取值——与取消政策同一套回退。
  • 出参随行下发生效值 min_stay_nights + 来源 min_stay_nights_source（unit/project/default）。
你们要改什么：不用改。不传户型级 = 完全按现状（房源级 → 频道默认）。

6房源属性 API：房间档案 21 字段

units.room_profile 新开放写入

入驻「房源字段」表（Excel）里的字段，统一放在户型级 room_profile，经 units/create / units/update 的 room_profile 对象写入，C 端详情页「房间档案」卡直接渲染。 此前这些字段只能平台后台录入，现在对商家开放接口开放。

写入规则
  • 合并语义：传入的键覆盖同名键，未传的键保持原值；传 null 清除整块。
  • 白名单：不在下表内的键直接丢弃（不报错）。空值（null / 空串）视为未传。
  • 越界报错：枚举非法 / 数值越界 / 文本超长 / 图片地址非法 → 400， message 里带字段中文名与可选值（例：room_profile.smoking（吸烟属性）取值无效，可选：no / designated / allowed）。
  • 出参：units[] 里直接给已解析的 room_profile 对象，不用自己 parse ext 字符串。
{ "id": 3101,
  "room_profile": {
    "introduction": "面朝庭院，独立入户",
    "area_type": "building", "window_type": "exterior", "window_count": 2, "window_openable": true,
    "max_guests": 4, "max_adults": 3, "max_children": 1, "smoking": "no",
    "beds": "卧室1：1.8×2.0m 大床", "kitchen": "独立厨房 · 可做饭",
    "feature_image": "https://cdn.example.com/room.jpg"
  } }

9向后兼容承诺

不传新字段 = 行为逐字不变。具体来说：
  • 继续按 price_from + rent_monthly 传的房源：默认夜价与卡片展示价一分不变 （存量 132 个 rental 户型未配 price_night，已验证价格无变化）。
  • 继续用 qty（放出总量）的房源：剩余数算法逐字节不变（qty_base 为空的存量行按旧口径走）。
  • 不开启 default_closed 的房型：没推过的晚照旧可订。
  • 继续用 photos/add 的接入方：接口保留；只是重复推同一张图不再堆重复行。
  • 保租房 / 长租房源的 C 端卡片仍按月展示（¥X/月起），不受「旅居按晚」影响。
