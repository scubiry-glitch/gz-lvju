# 平台运营方操作手册（服务认证中台 P 端）

> 适用范围：搬家、保洁、维修、置换等本地生活服务全品类
> 系统入口：https://shenyang.meizu.life/screens/
> 版本：v1.0　·　适用后台：服务认证中台（P 端）+ 金融结算端（F 端）+ 监管端（G 端）
> 视角：**平台运营方**（区别于服务商操作手册的 B 端视角）

---

## 0. 系统总览

本系统围绕「服务认证中台 + 运营商工作台」双后台运转。**平台运营方（P 端）是标准的制定者、规则的执行者、交易的监管者**，与 B 端服务商的职责分工如下：

| 角色 | 界面 | 平台运营方职责 |
|------|------|---------------|
| **P 服务认证中台** | 类目、SPU、等级标准、题库、发证、信用、流量、分账、工作流 | 定标准、发规则、管准入、控交易 |
| **F 金融结算端** | 监管账户对账、结算付款、结算账户配置 | 资金托管、分账、对账 |
| **G 监管端** | 白名单审定、投诉、检查、公示 | 双审背书、合规监管 |
| B 运营商工作台 | 商家 SKU、排班、服务者、派单 | 日常经营（服务商手册已覆盖） |

**平台核心能力架构（P 中台控制台）：**
- 5 类机构统一管理：S 服务者 / B 运营商 / V 人力服务商 / M 物资供应商 / T 培训机构
- 1 个公共底座：发证管理、信用规则、数据中台、权限 RBAC、工作流、Webhook、API 网关、通知
- 核心公式（平台侧视角）：**可售 SKU = 平台 SPU + 本店服务者 + 价格**，SPU 与标准工序由平台统一定义，商家不可改
- 平台核心资产：等级标准（L0–L7）、题库试卷、信用规则（42 条）、流量策略（7 条）、分账规则（分级抽佣矩阵）

**权限提示：** 管理台写接口已启用鉴权，页面自动携带 API Key（默认 `dev-juzhu-key`，可 localStorage.JUZHU_API_KEY 覆盖）。P 端角色权限由 RBAC 控制（超管/中台运营/监管员/审计员/DPO 等 14 角色，186 权限点）。

## 1. 基础数据录入（平台侧）

基础数据分四层：**服务子类目（P）→ 标准品 SPU（P）→ 等级标准与题库（P）→ 商家 SKU（B）**。前三层全部由平台运营方维护。

### 1.1 服务子类目管理（P 服务认证中台）

**入口：** 控制台 → 服务认证中台 → 服务子类目管理（`p-jz-category.html`）

子类目决定服务类目下的细分场景，是 C 端展示的最小分类单元：

| 大类目 | 代码 | 覆盖业务 |
|--------|------|---------|
| 🧹 保洁 | cleaning | 日常清洁、深度清洁、家电清洗 |
| 🔧 维修 | repair | 家电维修、管道疏通、门窗灯具 |
| 🚚 搬家 | moving | 居民搬家、长途搬家、企业搬迁 |
| 🤱 月嫂/保姆 | nanny | 住家保姆、育儿嫂、月嫂、护理 |

> **置换业务提示：** 若新增「置换」等业务，需先在中台新增子类目（如「家具置换」「家电以旧换新」），再在其下建 SPU，否则 B 端无法创建对应 SKU。

**操作步骤（新增/上下架子类目）：**
1. 点击「+ 新增子类目」
2. 填写：所属大类目（cleaning/repair/moving/nanny）、名称（≤20 字）、图标（emoji）、排序（越小越靠前）、状态（上架 on / 下架 off）
3. 保存后按大类目分组展示，KPI 显示各大类目子类目数

**平台运营要点：**
- 删除前系统校验「无产品引用」，被 SKU 引用的子类目不可删除，只能下架；
- 下架后 C 端立即不再展示该类目，影响商家在售 SKU 曝光，需提前通知商家。

### 1.2 服务标准品 SPU（P 服务认证中台）

**入口：** 控制台 → 服务认证中台 → 服务标准品 SPU（`p-jz-spu.html`）

SPU 是平台统一定义的**标准服务品**，含标准工序、参考时长、参考价、最低服务者等级。商家引用 SPU 组成可售 SKU。

**操作步骤（新增 SPU）：**
1. 点击「+ 新增 SPU」
2. 填写：
   - **所属类目**：cleaning / repair / moving / nanny
   - **slug**（≤40 字符）：英文唯一标识，如 `deep-clean-4h`
   - **SPU 名称**（≤30 字）+ **规格说明 spec**（≤60 字）
   - **参考价 price_from + 价格单位**（如 128 / 「起」）、**参考时长（分钟）**
   - **最低服务者等级**：L1–L5（决定派单时服务者匹配门槛）
   - **标签 tags**（逗号分隔，如「热门,最快2小时上门」）
   - **标准工序 service_flow**：平台统一标准，**商家不可修改**（如「上门核对,标准工序作业,完工验收,记录回传」）
   - **排序、状态**（上架 enabled / 下架 disabled）
3. 保存后按类目分组展示「被 SKU 引用」计数

**平台运营要点：**
- SPU 的**标准工序是服务质量的基线**，平台需按品类持续维护（保洁/维修/搬家工序差异大）；
- 被引用的 SPU 只能下架不能删除；下架前先检查在售 SKU，避免商家商品失效；
- **新增品类（如置换）时，SPU 是第一步**：先建类目 → 再建 SPU 定义工序/价格锚点 → 商家才能建 SKU。

### 1.3 等级与技能矩阵（L0–L7）

**入口：** 控制台 → 等级与技能矩阵（`p-standards.html`）

L0–L7 八级定义、晋级条件、11–12 工种 × 6 维能力矩阵，是服务者准入、派单权重、分账比例的总纲。

| 等级 | 名称 | 定位 | 基础分润 | 到账周期 |
|------|------|------|---------|---------|
| L0 | 注册准入 | 实名+资料+背调 | 不参与计费 | — |
| L1 | 基础认证 | 仅师傅带单（50% 分润给师傅） | 带单制 | — |
| L2 | 独立服务 | 基础流量基线 | 70% | T+15 |
| L3 | 高级管家 | 复杂场景+复购绑定 | 77.4% | T+7 |
| L4 | 督导/店长 | 优先派单+团队工单 | 82% | T+5 |
| L5 | 服务商负责人 | 独立结算轨道 | 88% | T+3 |
| L6 | 平台认证讲师 | 按课时结算 | 培训分成 | — |
| L7 | 区域级专家 | 行业标杆·独立轨道 | 按项目 | — |

**平台运营要点：**
- 等级标准支持「版本管理」：新建版本 → 灰度 → 发布，发布后影响派单权重与分账（如 L5 流量权重 ×3 → ×2.5 曾触发防垄断调整）；
- 晋级条件含硬指标（在岗时长、完结单量、客评、学时、综合考、复杂工单、信用分），平台需定期校准门槛；
- L5+ 是经营/培训/标准角色，走独立结算轨道；L1–L4 才是交易主体。

### 1.4 题库与试卷（准入考试的内容底座）

**入口：** 控制台 → 题库与试卷（`p-question-bank.html`）

- 题目总数 1,248 道，覆盖 6 类核心岗位 + 6 类延伸岗位（检修、保洁、服家、装修交付、四保一服、服务商负责人）；
- 题型：单选/多选/判断/情景实操；按章节、难度、区分度管理；
- 试卷模板 84 套，与 L0–L7 等级口径对齐；
- 平台运营要点：**高错率题目告警（错率>80%）**、低区分度题目改版、情景实操题需人工批改——这些都是平台要盯的题目质量指标。

### 1.5 保障方案与责任险（投保前置）

**入口：** 控制台 → 公共底座 → 履约保障与责任险（`p-insurance.html`）

| 保障产品 | 覆盖 | 保额 | 说明 |
|---------|------|------|------|
| 服务者责任险 | 人身/第三者财物/纠纷 | 最高 ¥50 万/次 | 平台统投，**必投保才可接单** |
| 履约保证金 | 爽约/违规/不达标先行赔付 | ¥2,000 起 | 可信用替代，江苏银行监管账户 |
| 客房安心险 | 家电家具损坏 | 最高 ¥10 万 | 对接 F 金融 |
| 家财险 | 房源端财产保障 | 最高 ¥10 万 | 运营方投保 |

**平台运营要点：**
- 保费 ¥18/月平台统一议价；信用分 >4.5 保费 8 折（信用联动保费）；
- 理赔流程：在线报案 → 联合定损 → 责任认定+信用记录关联 → 江苏银行 T+3 划付；
- **无责任险不得接单**——这是服务者准入的硬门槛，理赔结果回流信用引擎。

### 1.6 信用规则引擎（平台的风控大脑）

**入口：** 控制台 → 信用规则引擎（`p-credit-engine.html`）

- 42 条规则：加分 18 / 扣分 14 / 阈值告警 6 / 冻结解冻 4，作用域覆盖 5 类机构（S/B/V/M/T）；
- 典型规则：R-001 五星好评 +1.5、R-002 月度全勤 +5.0、R-018 复杂工单 +3.5（灰度）、R-006 师傅带徒成功 +6.0、R-201 投诉受理 −4.0、R-205 退单偏高 −2.4；
- **支持规则模拟器**：选一名服务者预演新规则上线后 30 天信用变化，再决定灰度比例；
- 平台运营要点：规则支持**灰度发布（CANARY）**、漂移检测、版本对比（v3.2 生效 / v3.3 灰度 5%）。

## 2. 服务商准入（V/B/M/T 四类主体）

平台运营方的准入职责覆盖四类机构：**V 人力服务商（入驻+LV）、B 运营商（白名单+评级）、M 物资供应商（品类认证）、T 培训机构（合作伙伴认证）**。

### 2.1 入驻申请受理（统一入口）

**入口：** 控制台 → 入驻申请受理（`p-onboarding-review.html`）

六步入驻的**中台受理端**：服务者/服务商提交 → 实名+资质核验 → 建档转培训。

**受理字段：**
- 主体类型：服务者 / 服务商（机构）
- 实名认证：身份证 + 人脸 + **人社职业资格库比对**（全程网办，一次核验）
- 资质上传：职业证书 / 营业执照 / 负责人信息
- 申报工种：旅居管家 / 家政 / 向导 / 保洁…
- 服务区域：按设区市 + 服务站

**操作步骤：** 受理队列（待审/已建档/已转培训）→ 查看材料 → 通过/驳回 → 建档并分配学习任务 → 转培训（STEP 2）。支持**批量受理**与**导出名册**。

### 2.2 负责人商业认证 L5（机构派单资格）

**入口：** 控制台 → V 服务商 → 负责人商业认证 L5（`p-vendor-cert.html`）

L5 是机构经营轨道的关键认证，**授牌即获机构派单资格**。门槛：

| 维度 | 要求 |
|------|------|
| 经营资质 | 营业执照 + 行业经营许可 |
| 团队持证率 | 在岗服务者 L2+ 占比 ≥ 80% |
| 负责人能力 | 通过 L5 商业认证考（经营/合规/资源） |
| 履约保障 | 缴纳保证金 + 团队责任险全投保 |
| 服务规模 | 累计服务单量 + 客户评价 ≥ 4.5 |

**认证流程（P + 住建双审）：** 申请 → 资质审核（执照+持证率核验）→ 经营评估（规模/口碑/履约记录）→ 商业认证考（机考）→ **授牌**（L5 证书+机构派单资格）。授牌结果同步住建厅白名单与公示门户，可扫码验真。

### 2.3 B 运营商白名单审定（机构准入核心）

**入口：** 控制台 → B 白名单运营商 → 白名单审定（`p-b-whitelist.html`）

**LV 分级标准：**
- **LV1 单城**：市级运营，1000 套以下，入网 6 个月内
- **LV2 跨市**：多城联动，5000 套以下，入网 1 年+续约 ≥1 次
- **LV3 省级**：全省覆盖，5000 套以上，同业标杆，参与标准制定

**双审制流程（~45 天）：**
1. 受理申请（企业资质+法人+业务范围）→ P 中台运营
2. 资质初审（营业执照+5 年托管经验+项目佐证）→ 贝壳初审组
3. 财务与诉讼背景（重大诉讼+注册资本+信用穿透）→ 第三方尽调
4. 合规终审（租金 ≤90% 市价+押金合规+投诉率历史）→ 江苏住建厅
5. LV 评级（套数/跨市能力/同业评分）→ P 中台+省房协
6. 公示与上链（入网公示 30 天无异议+区块链留痕）→ G/P/Portal

**平台运营要点（防垄断红线）：**
- 同业开放保护：任何运营商（含贝壳省心租）市占率**不超过 30%**；
- 持有方可同时委托 ≥2 家运营商（避免锁定）；
- 集采底价与流量分配对全部白名单运营商同业并列，不向关联方倾斜；
- 公平竞争审查每年 1 次，3 年中评 + 5 年回看（当前同业开放评分 94/100）。

### 2.4 M 物资品类认证（置换/维修的供应链底座）

**入口：** 控制台 → M 物资供应商 → 6 品类认证审核（`p-m-catalog-cert.html`）

6 物资品类全覆盖：🪵 家具（环保 E0·防火）· 🌀 家电（能效1级·3C）· 🧱 建材（甲醛 E0）· 🔒 智能锁（公安认证）· 🎨 涂料（VOC 达标）· 🚿 卫浴（节水1级）

**6 步认证流程（~60 天）：** 资质（营业执照+三年质保承诺）→ 检测（第三方检测报告）→ 抽检（现场抽检+样品送检）→ LV 评级（品类数+集采能力）→ 底价（省级集采底价确认）→ 终审（住建发证+公示）

**LV 标准：** LV1 单品类 / LV2 多品类（≥2，省级集采资格，抽检合格率 ≥99%）/ LV3 全品类（6/6，参与制定集采底价）

> **置换业务联动：** 「以旧换新/家具家电置换」涉及新品配送与旧品回收，M 品类认证是准入前提；批次质检（`p-m-batch-qc.html`）实现扫码追溯，不合格批次触发信用扣分+重发（如 VOC 超标 −5 信用）。

### 2.5 T 培训机构认证（人才供应链）

**入口：** 控制台 → T 培训机构 → 合作伙伴认证（`p-t-partner-cert.html`）

- **LV1 基础培训**（L0–L1 范围，L5 讲师 ≥1，可发学时证明）
- **LV2 进阶培训**（L0–L3 ≥12 门+实操，L5≥2+L6≥1，可签发 L3 证书+题库共建 ¥80/题）
- **LV3 省级合作**（L0–L7 全覆盖，L6≥3+L7≥1，参与标准制定）
- 讲师持证体系 L5→L7 独立轨道（L6 讲师 ≥200h 授课，L7 区域专家 ≥1000h+标准制定 ≥1 项）
- 平台运营要点：课程须对位 P 中台 11 工种 × L0–L4 等级标准，学员通过率门槛 LV1≥80%/LV2≥85%/LV3≥90%。

## 3. 服务者准入（S 主体全链路）

服务者准入是**「入驻受理 → 培训认证 → 考务考试 → 结业学时 → 发证上链 → 投保 → 白名单」**七段链，全部由平台运营方（P）+ 住建厅（G）双审把关。

### 3.1 服务者入驻受理（STEP 1）

**入口：** 控制台 → 入驻申请受理（`p-onboarding-review.html`）

- 在线提交（App/门户填表+上传资质）→ 实名核验（人脸+人社职业资格库比对）→ 资质审核（证书真伪+工种匹配）→ 建档（生成档案+分配学习任务）→ 转培训
- 平台运营要点：**对接江苏人社职业资格库**，实名与资格一次核验；受理 SLA 建议 <1 天（工作流模板统计 L0 准入闭环 98.6%·<1d）。

### 3.2 课程认证（STEP 2·培训内容准入）

**入口：** 控制台 → T 培训机构 → 课程认证审核（`p-course-cert.html`）

课程全链路：课程开发 → **课程认证** → 上架培训中心 → 学员学习 → 结业考试 → 考务成绩 → 结业学时 → 统一发证。

**认证标准：** 等级对位（匹配 L0–L7 标准）+ 考纲备案（题库+通过线）+ 讲师持证（主讲 ≥L6，挂靠 LV2+ 机构）+ 课时与实操比例达标 + 年度复审。

**认证流程：** 提交课程（大纲+课件+讲师）→ 大纲审核 → 考纲备案 → 试讲评审（L7 专家打分）→ 发证上架。无考纲的课程直接退回（如「夜间安保速成」）。

### 3.3 考务排考与成绩核发（STEP 3）

**入口：** 控制台 → 考务·排考与成绩核发（`p-exam-admin.html`）

- 承接 T 培训机构提交的**排考申请**（14 待审示例），平台统一安排考点/监考/防作弊；
- 考试形式：机考 + 情景实操 + 答辩；机考自动判分、实操人工复核；
- 成绩核发后自动生成准考证、推送考生 S 端，并向 T 机构回执；
- 平台运营要点：成绩核发 SLA **T+1 内（核发率 99.2%）**；不及格/复核挂起/退回补学分别处理。

## 7. 常见问题（FAQ）

**Q1：平台新增一个品类（如置换）要走什么流程？**
A：① 新增服务子类目 → ② 新增 SPU（定义标准工序/参考价/最低等级）→ ③ 通知商家建 SKU → ④ 如需物资联动，走 M 品类认证 → ⑤ 配置该品类的分账比例与流量策略 → ⑥ 上架后监控订单漏斗。

**Q2：服务者为什么在 C 端搜不到？**
A：按链路排查：① 是否完成入驻建档 → ② 是否通过培训考试并拿到证书 → ③ 证书是否上链公示 → ④ 是否投保责任险 → ⑤ 是否在 G 端服务者白名单 → ⑥ 商家是否将其勾选到 SKU。六环缺一即不可接单。

**Q3：证书吊销后会发生什么？**
A：吊销走审批流（触发 → 风控判定 → 主管批 → 公示同步），吊销后：服务者等级失效、不可接单、白名单移除、多端广播（短信/App push/微信/公示门户/邮件），且吊销记录关联信用分。

**Q4：结算被锁付是什么原因？**
A：通常为对账不符、订单异常或账户问题。先核对结算清单与订单流水，处理争议/退款/优惠后，在下一结算窗口解除锁付。

**Q5：规则/策略调整如何安全上线？**
A：平台标准做法：新建版本/草稿 → 规则模拟器预演（如信用规则）或 A/B 实验（如流量权重）→ 灰度发布（CANARY 5%）→ 观察漂移与误判 → 全量发布。重要策略（如 L5 权重）需同时过防垄断检测（基尼系数、市占率）。

**Q6：B 端和 P 端都能派单，边界在哪？**
A：B 端负责本机构订单的日常派单（快速派/手动派）；P 端制定派单规则（流量倾斜策略）并在工单池做兜底派单与全量交易监控。客户指定服务者优先（from_customer），否则按规则轮询。

**Q7：Webhook 死信队列怎么处理？**
A：死信 = 投递失败事件（当前 14 条），需人工查看失败原因（订阅方地址变更/限流/超时），修复后重放；持续失败需联系订阅方或下线订阅。

**Q8：API Key 是什么？**
A：管理台写接口的鉴权密钥，默认 `dev-juzhu-key`，可通过 localStorage 的 `JUZHU_API_KEY` 覆盖。正式环境请使用分配的生产密钥并妥善保管。
