1 接入概览

房源开放接口是平台商家开放接口的房源分支：路径前缀 /api/juzhu/housing/vendor/*，全部为 POST，请求/响应均为 JSON。鉴权、密钥、错误码风格与家政开放接口（/api/juzhu/jiazheng/vendor/*）完全一致，一套密钥两个业务共用。

  • 提交即生效：房源与户型实时可查，逐晚房态即时更新；客户订单占用的晚自动锁定，任何接口都不可改。
  • 数据归属：房源创建时自动绑定签约商家，所有读写按归属隔离——查询、更新、上下架只能命中自己的房源，他人房源一律 404（不泄露存在性）。
  • 上架语义：status ∈ draft（草稿，默认）/ online（上架）/ offline（下架）；C 端目录只出 status=online 且 rating_status=passed（双闸）。目录有 ≤ 15 秒缓存，上下架最迟 15 秒生效。
  • 审核语义：新建一律先落草稿（传 online 创建会被拒）；上架前须通过平台评级审核（rating_status：draft → pending → passed / rejected），提审与查进度走开放接口 projects/rating/submit / projects/rating/status（见 4.11）。已上架房源的内容更新免审即时生效。

接入流程

1开通凭证平台为商家配置接入密钥，线下下发 vendor_id + hmac_key。
2沙箱联调用调试台或脚本签名调通 regions/list + projects/list（只读）。
3创建房源projects/create 建草稿（默认不入 C 端），补户型、图片与价格。
4评级提审projects/rating/submit 提交自评分进入平台复核，projects/rating/status 查进度与驳回原因。
5上架运营审核通过后 projects/status 上架；日常用房态接口做关房/夜价，随用随调。

2 HMAC 签名认证（与家政开放接口同机制）

2.1 凭证

每个商家一个 vendor_id + 一把 hmac_key，由平台统一配置并线下下发。hmac_key 等同密码：只放服务端或自己的联调机，不要写进前端代码、不要提交仓库。

2.2 签名算法

  1. 取业务参数对象 body，加上 vendor_id；剔除 sign 字段。
  2. 扁平化：嵌套对象用 父键.子键 点号展平；null、''（空串）的键不参与签名。
  3. 值序列化：字符串原样；数字/布尔转字符串（true→'True'、false→'False'）；数组 → ['a', 'b']（单引号、逗号空格分隔）。
  4. 按键名字典序排序，拼成 k1=v1&k2=v2&…（& 连接，无转义）。
  5. 追加 timestamp（毫秒时间戳）参与上述串；用 hmac_key 做 HMAC-SHA256，取 hex 小写 为 sign。
  6. 请求体 = 业务参数 + vendor_id + timestamp + sign，POST JSON 发送。时间戳与服务器偏差 ±5 分钟 内有效。
// Node 签名示例
const crypto = require('crypto');

function pyStr(v) {
  if (v === true)  return 'True';
  if (v === false) return 'False';
  if (Array.isArray(v)) return '[' + v.map(x => (typeof x === 'string' ? "'" + x + "'" : pyStr(x))).join(', ') + ']';
  return String(v);
}
function flatten(data, prefix) {
  const flat = {};
  for (const [k, v] of Object.entries(data || {})) {
    if (v == null || v === '') continue;          // 空值不参与签名
    const key = prefix ? prefix + '.' + k : k;
    if (v && typeof v === 'object' && !Array.isArray(v)) Object.assign(flat, flatten(v, key));
    else flat[key] = pyStr(v);
  }
  return flat;
}
function sign(secretKey, body) {
  const payload = { ...body };
  delete payload.sign;
  const timestamp = Date.now();
  const flat = flatten(payload);
  flat.timestamp = String(timestamp);
  const stringToSign = Object.keys(flat).sort().map(k => k + '=' + flat[k]).join('&');
  payload.timestamp = timestamp;
  payload.sign = crypto.createHmac('sha256', secretKey).update(stringToSign, 'utf8').digest('hex');
  return payload;                        // 直接作为 POST body
}

const body = sign(HMAC_KEY, { vendor_id: VENDOR_ID });
await fetch(BASE + '/api/juzhu/housing/vendor/projects/list', {
  method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(body),
});
易错点：① 数组参与签名用单引号形式（tags=['演示', '回归']），与 JSON 序列化不同；② 嵌套对象（如 units 数组里的对象）会被点号展平进签名，直接把最终 body 交给 sign 函数即可，不要手工拼；③ 重试时须重新签名（timestamp 会过期）。

响应统一为 JSON：成功 { "code": 0, "message": "success", … }；失败 HTTP 状态码 + { "code": 4xx, "message": "原因" }（见 错误码）。

3.4 卡片展示价（最低可售单夜价）

C 端房源卡上的价格由平台计算并随接口下发（price_from_display / price_unit / price_note），贵方无需传、也不要在自己页面另算一套。单位口径：minsu 与带「旅居」tag 的 rental 按晚；其余 rental 按月（起价语义，price_from 缺省时回落户型默认夜价 × 30）。

按晚房源的取值规则：从今天起按自然月向后扫描（最多 12 个月，与 C 端可订窗口同口径），取第一个存在可售间夜的月份，该月内最低单夜价即展示价；扫满仍无可售 → 不展示价格，文案「暂无可订」。

某一晚的情况能不能卖单价取谁
没有房态记录（默认态，绝大多数晚属于这种）✅ 能默认夜价（price_night > 月租/30 > 起价/30）
有记录，blocked（关房）❌ 不能—
有记录，open + 有覆盖价✅ 能该覆盖价
有记录，open + 无覆盖价✅ 能默认夜价
该晚已订满（remaining ≤ 0）❌ 不能—
常见误解：「查房态 status=open 的记录」是不够的——平台库存模型是没有记录 = 默认可订，差异行只在关房 / 改价 / 改放出间数 / 被订时才产生。若只扫有记录的晚，会把绝大多数可订房源误判成「暂无可订」。

3.5 净可售库存（available_qty，多渠道商家）

如果同一批房间你们同时在别的渠道卖（OTA、直客、自己的小程序…），或者有房间临时不可售（未保洁、维修），用 available_qty 比 qty 更省事：直接把「这一晚平台还能卖几间」推上来，按你们自己的口径算就行。

字段语义平台怎么算 remaining
qty（旧）该晚对平台开放的总量，含平台已卖掉的max(0, qty − 已订)——所以你们必须先查一次平台已订多少，有竞态
available_qty（推荐）该晚净可售，按你们的口径（已扣他渠道与不可售）记下推送时点的已订数作基线，clamp(可用 − (已订 − 基线), 0, 物理余量)——平台之后卖掉的才扣，取消自动加回，无需你们再算

举个你们反馈里的例子：房型 total_qty=6，平台已售 2、其他渠道售 1、还有 1 间未保洁 → 你们算出「能卖 2 间」，直接推 available_qty: 2：

  1. 推送时平台已订 2 → 基线记 2 → 平台显示剩余 2（旧口径会二次扣成 0）；
  2. 平台又卖掉 1 间 → 剩余 1；客户取消 → 自动回到 2；
  3. 其他渠道又卖掉 1 间 → 你们重推 available_qty: 1，基线刷新为当时的已订数 → 剩余 1。
防超售兜底：如果推的净数超过实际剩下的房间数（比如对账漏了他渠道的销量），平台按物理余量 total_qty − 已订 封顶，不会卖超。所以推大不会超售，推小才会少卖——对账宁可略保守。
两个口径别混：qty 与 available_qty 同一次调用只能传一个（同时传 400）。任一时刻该晚只属于一种口径；用 qty 写回会把基线清空，回到旧语义。

3.6 默认关房（default_closed，可选开关）

净可售解决的是「推过的晚怎么算」，默认关房解决的是「没推过的晚怎么办」。默认情况下平台是「没推过的晚 = 可订、放出量 = total_qty」——对多渠道商家这很危险：你们在别处卖掉、或临时不可售的晚，只要没推过，平台照样会放出去卖。

把房型的 default_closed 设为 true（写 units.ext，可经 units/update 或后台配置）后：

  • 只有你们显式推送过放出量的晚才可订（qty 或 available_qty 都算）；
  • 没推过的晚一律不可订（remaining = 0，下单 400）；只设过夜价、没设放出量的晚也算没推过；
  • 缺省关闭——不配置的房源行为与现在完全一致；只作用于指定户型的预订，整栋单（不指定户型）语义不变。

建议需要多渠道对账的房型开启，并按「未来 12 个月」滚动推送放出量（见 5.1）。

Webhook 事件通知（平台 → 商家）

客户动作触发的订单变更，平台会主动推送签名事件到你为商家配置的通知地址（接入单里提供 URL 即可），不必轮询等单：

event触发时机商家应做什么
booking.created客户提交预订单备房；预付单等待支付到账
booking.paid预付单支付完成（民宿民宿）此时方可确认订单
booking.cancelled客户取消（商家自己拒单不会推送）释放已备房源

推送为 POST JSON，body 即开放接口同款结构：event + vendor_id + order（订单对象，手机号不外传）+ timestamp + sign。验签与开放接口同一算法（对去掉 sign/timestamp 的参数扁平排序后 HMAC-SHA256），收到后先验签再处理：

// Node 验签示例（与平台 hmac_auth.cjs 同算法）
app.post('/hooks/booking', (req, res) => {
  const body = req.body;
  const payload = { ...body };
  delete payload.sign;
  const flat = flatten(payload);              // 与请求签名同一套 flatten
  flat.timestamp = String(body.timestamp);
  const expect = crypto.createHmac('sha256', HMAC_KEY)
    .update(Object.keys(flat).sort().map(k => k + '=' + flat[k]).join('&')).digest('hex');
  if (expect !== String(body.sign).toLowerCase()) return res.status(401).end();
  // 处理 body.event / body.order …
  res.status(200).end('ok');                    // 2xx 即视为送达
});
送达语义：非 2xx 或超时（5s）视为失败，按 5s / 30s / 120s 重试 3 次后放弃——Webhook 是「尽力通知」，不担保必达；请以 bookings/list 定时对账兜底（推荐粒度：每分钟拉一次 status='pending'）。订单明细里不含客户明文手机号。
完整业务流（商家视角）：创建房源（草稿）→ 补价与户型 → 上架 → 房态/夜价日常维护 → 收 Webhook（或拉单对账）→ 确认或拒单 → 入住 / 离店；任一环节失败都会返回明确的 400/404 与原因（见 错误码）。

5.1 批量设置房态 / 夜价 / 放出间数

POST/api/juzhu/housing/vendor/stay-calendar/set关房 / 开房 / 夜价覆盖 / 放出间数覆盖（多间口径 2026-09-10），单次 ≤ 400 晚
{

  "dates": ["2026-12-10", "2026-12-11"],
  "status": "blocked",                 // blocked 关房；open 开房
  "price_night": null,                 // blocked 可同时设价；open + 价格 = 夜价覆盖；open + null = 不改价
  "qty": null,                         // ★ 放出总量覆盖（1-999，仅房型级）：open + qty = 该晚只放 N 间；不传 = 用 total_qty
  "available_qty": null                  // ★ 净可售（0-999，推荐，见 3.5）：与该晚的 qty 二选一；写回 qty 会把基线清空
}
→ 200 {

  "days": [                          // 推完即可对账（不必再查一次日历）
    { "date": "2026-12-10", "status": "open", "qty": 2, "qty_base": 2,
      "available_qty": 2, "booked_qty": 2, "remaining": 2 }

  • 已订晚（booked_qty>0）不可关房：返回 400 并列出日期，须先取消订单；改价 / 调放出量不受限。

  • 覆盖价参与下单计价（2026-09-10 起）：订单金额 = 逐晚「覆盖价 || 默认夜价」合计 × 间数。周末 / 节假日分档 = 把对应日期批量 open + price_night；平日不传即回落默认。订单占用不清除当晚覆盖价，取消释放后商家差异行（价 / qty / 关房）原样保留。

5.2 最短连住（min_stay_nights）

旅居/短住按连续入住售卖：平台缺省口径为 rental=15 晚、minsu=15 晚。商家可覆盖，2026-09 起生效顺序为「户型 > 房源 > 频道默认」：户型级写 units.ext.min_stay_nights（units/create / units/update 直接传 min_stay_nights），房源级 projects.ext.min_stay_nights 降级为房源默认值。取值范围：rental 1–365 晚，minsu 15–365 晚、不得低于 15 晚（越界返回 400）。

整栋单（下单不指定户型）按排序最前的户型取值——与取消政策同一套回退，因此「最短连住」和「取消政策」两条住宿规则都可以只在户型上配，不必记住哪个在房源、哪个在户型。

三处同口径校验：C 端日历选段、下单页、平台下单接口 POST /api/juzhu/booking（不足返回 400「该房源须连住至少 N 晚」）。下单成功即占用这些晚，取消自动释放。户型数组与房态日历出参均随行返回生效值 min_stay_nights，页面直接读，不要回落到房源级或自设默认值。

5.3 房源交易能力（online_booking / online_payment）

projects/create / projects/update 按房源配置两个独立布尔能力：online_booking = 客户在线选房并提交订单、商家确认后线下收款；online_payment = 客户在线选房后进入收银台、支付完成再由商家确认。两项可同时开启，但至少开启一项，与 rental/minsu 频道无关；新建时两项均省略则默认仅开启 online_booking。两项都开时，C 端由客户选择；接口下单用 transaction_mode: "booking" | "payment" 指定，缺省优先 booking。catalog / 详情 / 房态日历出参均返回两个能力位，并保留 bookable 作为“至少一项可用”的兼容汇总字段。

我不按月租卖，只按每晚定价，可以吗？可以（2026-09 起）。给户型的 price_night 即可，rental 频道同样生效；rent_monthly 与 price_from 都可以不传。默认夜价顺序 = price_night > 月租/30 > 起价/30。
不传 price_from，C 端卡片价格显示什么？按展示价三件套（3.4）自动算：带「旅居」tag 的 rental 与 minsu 按晚，取最低可售单夜价（从今天起按自然月向后扫 12 个月，取第一个有可售间夜的月份内的最低价）；其余 rental 按月，起价缺失时用户型默认夜价 × 30。全窗口无可售时卡片显示「暂无可订」。贵方无需做任何事。

房间档案（简介 / 窗户 / 床位 / 入住人数…）怎么传？走户型级的 room_profile 对象（2026-09 开放，见 3.7）：units/create / units/update 传 room_profile: {...} 即可，只合并传入的键、未传的保持原值，传 null 清除整块。字段清单与取值范围见 3.7；越界会 400 并报出字段中文名与可选值。
抽检拉图会不会拖慢上架？拉不到图怎么办？只拉 2 张、只读必要字节、不落盘。仅网络不可达（超时 / DNS / 非 200）时放行并在响应里回 warnings——你们的 CDN 抖动不会卡住上架；只有确定性不合格（超 10MB / 小于 800×600 / 非图）才拒绝。

promo_price 会影响成交价吗？不会，当前是「首月特惠」展示标签位；营销价真实成交需另行排期。
amenities 没有枚举怎么映射？按下表 10 个 id 传（3.2）：ac / washer / fridge / heater / lock / wifi / tv / hood / microwave / induction。不传 = C 端回落展示全部；未知 id 不渲染。枚举字典化在平台排期。

owner_vendor_id 是什么？签名商家自动写入的数据归属标记，不可传不可改；一切接口按它行级隔离，订单佣金按它取商家档费率。

上架后更新房源信息要重新提审吗？外网会下架吗？不须提审、不下架：内容更新免审即时生效（目录 ≤ 15 秒缓存），外网持续可售。当前契约即「免审直更」，如业务要求重大变更走审核请向平台提出。
房态 / 房价日历最长设多久？C 端展示多久？单次 ≤ 400 晚、可滚动写更远；C 端可订窗口 = 当月起 12 个月，建议按 12 个月滚动维护。
某间夜的房态和价格必须同时传吗？不必，二者独立：blocked 关房；open + price 覆盖价；open + price:null 恢复默认价。一次调用一个 status 作用于整批 dates。

HTTPcode含义处置
401—缺失签名(sign)或时间戳(timestamp)参数检查签名三件套是否都在 body 里
401—请求已过期（±5 分钟窗口）校准服务器时间后重签
401—签名校验失败 / vendor_id 密钥未配置核对 hmac_key 与签名算法（数组、空值、嵌套展平）
400—name / city_id / project_id 等必填缺失按 message 补齐
400—channel 非法 / city_id 不属于商家开放城市 / district_id 不属于城市先用 projects/list 或平台侧确认主数据
400—上架被拒：有户型算不出默认夜价（缺 price_night/rent_monthly 且无 price_from，message 会点名户型）/ 无户型 / 照片不足 7 张 / 无封面 / 评级未通过 / 商家未过审按 message 补齐；评级走 rating/submit（4.12），图片走 photos/add（4.11）
400—下单被拒：该房源未配置价格，暂不可预订（2026-09 新增：算不出价不再 0 元成单）给户型补 price_night 或 rent_monthly（或房源起价）
400—评级：dims 缺维度 / 越界（0-5）/ 未知维度；或已在复核队列中重复提审按 4.12 维度表修正；进度用 rating/status 查
400—insurance 含未知标识 / min_stay_nights 超出频道范围（rental 1–365 / minsu 15–365）按 §6 / §5 枚举修正
400—qty 与 available_qty 同时传（语义不同，只能传一个）/ available_qty 超出 0-999 / 项目级传放出量见 3.5；项目级（unit_id=0）容量恒 1，不接受放出量
400—default_closed 非布尔传 true / false，null 清除（3.6）
400—room_profile 取值非法：未知枚举值 / 数值越界 / 文本超长 / feature_image 非法地址按 message 里的字段中文名与可选值修正（见 3.7）
400—photos/sync 入参问题：photos 空数组 / 未知 category / 同实体内 url 或 external_id 重复 / 非 http(s) 地址 / 声明分辨率低于 800×600 或超过 10MB见 4.11.1；错误信息会指明第几项（photos[i]）
400—上架被拒：图集抽检确定性不合格（超 10MB / 小于 800×600 / 非图）按 message 里的图片地址整改后重推；仅网络不可达不会拒绝（走 warnings）
400—房态：以下日期已有预订占用先取消订单再改房态
400—无可更新字段 / city_id 不支持修改按 message 调整
400—订单未支付不可确认 / 订单已取消不可变更支付走收银台后重试确认；取消为终态
404404订单不存在或不属于该商家（房源 / 户型同理）统一 404，不区分「不存在」与「越权」，防探测
