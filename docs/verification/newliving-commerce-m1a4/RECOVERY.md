# M1-A4 备份、恢复与发布回退记录

测试脚本：`node scripts/commerce/m1a4-backup-restore.cjs`（隔离环境实测）。原始数据：[recovery-results.json](recovery-results.json)。

## 1. 备份与恢复（REC-1/2）

- **方式**：`mysqldump --single-transaction --no-tablespaces`（一致性快照，不锁业务表）。
- **演练流程**：构造完整业务状态（配置发布、购买、预约、核销、结算执行并已付、到期退款已付）→ 记录业务指纹（10 张表行数 + 账务借贷合计 + 已付退款/付款金额）→ 全量备份 → **DROP 整库** → 从备份还原 → 逐项比对。
- **结果**：恢复前后指纹完全一致（订单/卡券/核销/批次/明细/指令/回执/追偿/赔付行数；借贷合计；已付金额）；`verifyInvariants` 全绿。
- **实测耗时**：备份与恢复 RTO 记录于 recovery-results.json（单库、本机 SSD，秒级）；生产 RTO 目标（≤4h）按库大小另行规划，方法不变。
- **数据恢复点**：备份写入时记录 `MAX(commerce_ledger_entries.created_at)` 与迁移版本——恢复点即最近一次成功备份时点；备份策略建议：每日全量 + binlog（binlog 配置属 DBA 侧，本阶段验证恢复路径本身）。

## 2. 迁移升级（REC-3）

- **演练**：将库回退到 001–003 状态（删除 004/005 表与迁移记录、去掉 redemptions 撤销列）→ 执行当前版本 `migrate`。
- **结果**：升级零业务数据变化（订单/卡券/核销/售后行数不变）；ALTER 幂等可重入；升级后不变量全绿（唯一允许口径差：004 退款单为空表——真实升级从备份恢复不存在此差）。
- **运维含义**：发布即"启动时自动迁移"；失败可重复执行；升级不锁旧版本数据结构之外的任何表。

## 3. 发布回退（REC-4）

- **演练**：`git worktree` 取出上一个已验收版本（HEAD 提交，不含本轮改动）→ 以旧代码对同一数据库启动服务 → meta/catalog 接口实测 → 关闭 → 比对业务指纹。
- **结果**：旧版本服务正常启动、核心接口可用；**业务历史与已记账务零变化**——旧代码对新增表（004/005）无感知，迁移版本表保留，前向升级无需任何处理。
- **生产回退步骤**：① `systemctl stop sy-commerce-preview`；② 恢复上一版本代码（git checkout 对应提交）③ `node scripts/commerce/install-preview.cjs`（或直接重启服务）；④ healthz + 运营统计页复核。**禁止**回滚数据库结构或删除业务表。

## 4. 边界

本轮在隔离库演练恢复路径与一致性；生产备份的调度、异地存放与 binlog 归档属 DBA 运维范围，需按同一方法定期演练。
