# M1-A4 性能报告

测试脚本：`node scripts/commerce/m1a4-perf.cjs`（独立临时 MySQL 库，跑完即删）。原始数据：[perf-results.json](perf-results.json)。

## 1. 环境（测试前登记）

| 项 | 值 |
|---|---|
| Node | v22.22.0 |
| MySQL | 8.0.45（本机） |
| CPU / 负载 | 2 vCPU 容器 / load ≈ 3 |
| 连接池 | 12（服务端与压测端各自） |
| 数据量 | 3 商户 × 3 门店 × 6 SKU、100+10 张真实兑换券、10,000 张种子券（万级结算） |
| 通过阈值（预先登记） | 业务 API P95 ≤ 1s（不含第三方等待）；零超卖 / 零超额预约 / 零重复业务结果；万级结算明细处理 ≤ 60s 且金额精确 |

## 2. 结果

| 场景 | 负载 | P95 | 结果 |
|---|---|---|---|
| 商品浏览 `GET /catalog` | 120 次顺序 | **7.5 ms** | PASS |
| 本人权益查询 `GET /my` | 120 次顺序 | **8.8 ms** | PASS |
| 兑换（含限流与幂等竞争） | 200 请求 / 20 并发路，100 码两账号竞争 | **455 ms** | PASS（恰好 100 成功，零超卖零重复） |
| 并发预约 | 50 请求抢 10 名额 | **154 ms** | PASS（恰好 10 成功，零超额） |
| 并发核销同一券 | 30 请求 | **109 ms** | PASS（恰好 1 成功，其余明确失败） |
| 万级结算明细 | 10,000 核销生成账单 | **3.9 s**（阈值 60s） | PASS；应结合计 = 10,000×8,000 分逐分精确；RSS 139MB |
| 万级批次提审+复核+执行 | 同一批次 | **0.35 s** | PASS；付款指令金额精确 |

## 3. 过程发现与处置

1. **并发预约死锁（真实缺陷，已修复）**：首订日 capacity 行不存在时 `INSERT IGNORE` 间隙锁在并发下死锁（ER_LOCK_DEADLOCK）。修复：先 UPDATE 缺行才 INSERT + 事务层死锁自动重试；修复后 50 并发全部按预期收敛。
2. **兑换限流（既有防护，测试适配）**：12 次/分/账号的防爆破限流在压测中以 429 快速失败——属预期防护；压测改为 12 个账号分摊负载后测得真实时延。该限流同时是运行手册中的「业务失败突增」告警的相关背景。
3. **连接池上限行为**：超过 pool 队列上限（12+50）的请求快速失败——作为过载防护记录在案；生产扩容仅需调整 `connectionLimit`。

## 4. 结论

约定负载下全部业务 API P95 ≤ 1s（不含第三方等待）；三种并发竞争场景零超卖、零超额、零重复；万级结算明细处理在阈值内且金额逐分正确。
