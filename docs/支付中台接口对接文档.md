# 支付中台接口对接文档

## 1. 文档说明

本文根据支付中台 `weapons.ke.com` 项目 `15453` 中以下 6 个接口整理：

1. C2B 支付下单：`1000086`
2. 关闭订单：`9276`
3. 订单结果通知（支付 + 退款）：`1501795`
4. 支付订单查询：`1493269`
5. 原路退款：`9297`
6. 查询退款单：`9264`

说明：

- 本文是为了本项目旅居民宿支付接入做的本地整理版。
- 原始接口 JSON 已保存到仓库临时目录：`.tmp/weapons_docs/*.json`
- 接口详情页来源：
  - `https://weapons.ke.com/project/15453/interface/api/1000086`
  - `https://weapons.ke.com/project/15453/interface/api/9276`
  - `https://weapons.ke.com/project/15453/interface/api/1501795`
  - `https://weapons.ke.com/project/15453/interface/api/1493269`
  - `https://weapons.ke.com/project/15453/interface/api/9297`
  - `https://weapons.ke.com/project/15453/interface/api/9264`

## 2. 总体结论

### 2.1 支付链路

- 支付下单接口是**同步下单**
- 支付结果以**异步通知**为准
- 主动查询接口用于补偿和兜底
- 关闭订单会让支付单进入失败/关闭态

### 2.2 退款链路

- 原路退款接口是**异步接口**
- 退款结果以**异步通知**为准
- 查询退款单接口用于补偿和兜底

### 2.3 对接重点

接入时至少要落地以下能力：

- 支付下单
- 支付结果回调
- 支付订单查询
- 超时/主动取消时关闭订单
- 原路退款
- 退款结果回调
- 退款查询补偿

## 3. 通用状态说明

### 3.1 支付订单状态

- `10`：已创建
- `20`：支付中
- `30`：支付成功
- `40`：支付失败 / 关闭 / 取消
- `50`：已申请退款

说明：

- `20` 是中间态，主动查询可能查到
- 支付中台不会主动通知 `20`
- `30`、`40` 会通过回调通知业务方

### 3.2 退款订单状态

- `1`：支付中台受理成功
- `10`：退款订单下单成功
- `20`：处理中
- `30`：退款成功
- `40`：退款失败
- `60`：已退汇
- `101`：分账回退初始化
- `102`：分账回退成功
- `103`：分账回退失败
- `104`：退款收银台受理失败

说明：

- 常规业务重点关注 `1 / 20 / 30 / 40 / 104`
- `101~103` 主要是分账回退场景

## 4. 订单结果通知

### 4.1 接口信息

- 标题：订单结果通知
- 文档 ID：`1501795`
- 方法：`POST`
- 路径：`/notice/order`

### 4.2 用途

用于接收：

- 支付订单结果通知
- 退款订单结果通知

### 4.3 回调返回约定

业务方接口必须返回固定字符串之一：

- `SUCCESS`：成功
- `NOTFOUND`：业务方没有找到回调里的数据
- `REPEATED`：收到重复终态回调

文档强调：

- 业务方收到回调后应**直接处理回调数据**
- 不建议在回调处理里再同步查询支付中台，否则容易导致回调超时

### 4.4 关键回调字段

- `appCode`：接入标识
- `projectCode`：资金项目标识
- `orderId`：支付中台订单号
- `cashierOrderNo`：收银台订单号
- `appOrderId`：业务支付单号 / 退款单号
- `amount`：支付金额 / 退款金额
- `userFactPayAmount`：用户实际支付 / 实际退款金额
- `discountAmount`：优惠金额
- `orderStatus`：订单状态
- `tradeTime`：交易完成时间
- `errorCode` / `errorMessage`：失败码 / 失败原因

### 4.5 支付单明细 `payOrderInfoList`

回调中还会携带支付单列表，关键字段包括：

- `payCategory`：支付大类
- `payMethod`：支付方式
- `channelApplyNo`：渠道请求流水号
- `channelFlowNo`：渠道返回流水号
- `payNo`：支付成功流水号
- `remittancePayNo`：退款退汇单号
- `fundChannel`：渠道用户路径信息
- `payAmount`：支付/退款金额
- `payStatus`：支付单状态
- `tradeTime`：支付完成时间

### 4.6 注意事项

- POS 场景可能出现先通知失败、后又通知成功
- 所以本地状态推进必须允许终态修正
- 回调处理必须做幂等

## 5. C2B 支付下单

### 5.1 接口信息

- 标题：C2B支付下单
- 文档 ID：`1000086`
- 方法：`POST`
- 路径：`/order/v2/createOrder`
- 标签：`收银台支付订单`

### 5.2 请求头

```http
Content-Type: application/json
```

### 5.3 核心请求字段

#### 顶层字段

- `appCode`：接入标识，支付中台统一分配
- `projectCode`：资金项目标识
- `appOrderId`：业务订单标识，28 字符内
- `appOrderName`：业务订单名称，50 字符内
- `amount`：交易金额，单位元
- `payChannel`：付款渠道信息
- `payOrderInfo`：付款单信息
- `appClientInfo`：业务客户端信息
- `callBackInfo`：回调信息
- `recAndShareInfo`：收款/分账信息
- `contractInfo`：合同信息
- `userInfo`：用户信息

#### `payChannel` 关键字段

- `cashierType`：收银台类型
  - `1`：SDK
  - `2`：H5
  - `5`：微信小程序 API
  - `8`：PC 收银台
  - `13`：微信小程序收银台
  - `14`：收款 PC 收银台
  - `15`：收款 SDK 收银台
  - `16`：新版 PC 收银台
- `shareBizCode`：业务码
- `tradeInfo.tradeName`：交易名称
- `tradeInfo.tradeDesc`：交易描述

#### `callBackInfo` 关键字段

- `callbackUrl`：订单终态结果通知，必填
- `settleNoticeUrl`：订单资金结算通知
- `paidNoticeUrl`：支付单支付结果通知
- `bankAccountNoticeUrl`：存管账户到账通知

#### `payOrderInfo` 关键字段

- `expireTime`：订单过期时间，单位秒
- `note`：付款单备注
- `goods`：商品明细

#### `appClientInfo` 关键字段

- `appClientIp`：业务方端 IP
- `appType`：终端来源
  - `1`：SDK
  - `2`：H5
  - `3`：微信小程序
  - `4`：微信公众号
  - `5`：PC

#### `userInfo` 关键字段

- `userType`
  - `0`：非 ke 体系用户
  - `1`：A+ 用户
  - `2`：C 端用户
- `ucid`：支付用户 id

### 5.4 响应关键字段

- `data.orderId`：支付中台订单流水
- `data.cashierOrderNo`：收银台订单号
- `data.status`：订单状态
- `data.accessToken`：唤起收银台 token
- `data.url`：收银台 URL
- `data.cashierUrl`：新增收银台 URL
- `data.wxData`：微信小程序支付参数

### 5.5 实施建议

本项目对接时建议本地至少落库：

- 业务订单号 `appOrderId`
- 支付中台订单号 `orderId`
- 收银台订单号 `cashierOrderNo`
- 下单返回状态 `status`
- 收银台唤起参数 `cashierUrl / url / wxData`
- 支付回调终态

### 10.2 退款单主表

## 12. 当前项目现状与差距

### 12.1 当前实现现状

当前旅居民宿支付链路仍是 mock 方案：

- 下单接口 `POST /api/juzhu/booking` 会直接创建本地订单并占房态
- 支付接口 `POST /api/juzhu/booking/pay` 会直接把本地订单改成 `paid`
- 取消接口 `POST /api/juzhu/booking/cancel` 对已支付订单会直接把本地 `pay_status` 改成 `refunded`
- 支付页 `lvju-app-pay.html` 前端固定传 `pay_method: 'mock'`

### 12.2 当前代码位置

- 下单：`app.js` 约 `4616-4728`
- 查单：`app.js` 约 `4731-4765`
- 取消：`app.js` 约 `4767-4794`
- 支付：`app.js` 约 `4797-4827`
- 超时关闭：`app.js` 约 `744-775`
- 支付页：`lvju-app-pay.html` 约 `71-114`
- 下单成功跳支付页：`lvju-app-booking.html` 约 `445-485`
- 订单页状态展示：`lvju-app-orders.html` 约 `70-180`
- 支付成功页：`lvju-app-paid.html` 约 `61-87`

### 12.3 主要差距

和真实支付中台对接相比，当前缺失：

1. 支付下单时调用真实支付网关
2. 支付回调入口
3. 支付查询补偿
4. 关闭订单时调用真实关单接口
5. 原路退款接口
6. 退款查询补偿
7. 支付/退款流水表
8. 回调幂等与通知日志

## 15. 代码改动清单

### 15.1 后端

#### A. 新增支付网关封装模块

建议新增：

- `payment_gateway.cjs`
- `payment_service.cjs`

职责建议：

- `payment_gateway.cjs`：只负责调用支付中台接口
- `payment_service.cjs`：负责本地状态机、幂等、落库、回调处理

#### B. 改造 `POST /api/juzhu/booking/pay`

当前行为：

- 直接把 `booking_orders.pay_status` 更新为 `paid`

改造后行为：

1. 校验订单状态
2. 如果已存在未过期支付单，则直接返回现有收银台参数
3. 调用 `/order/v2/createOrder`
4. 落库 `payment_orders`
5. 返回收银台信息给前端
6. 不再直接把订单改为 `paid`

#### C. 新增支付回调路由

建议新增：

- `POST /api/juzhu/payment/notify`

处理逻辑：

1. 记录 `payment_notify_log`
2. 按 `appOrderId` 找到本地支付单 / 退款单
3. 幂等处理终态
4. 支付成功时更新：
   - `payment_orders`
   - `booking_orders.pay_status='paid'`
   - `booking_orders.pay_at`
5. 退款成功时更新：
   - `payment_refunds`
   - `booking_orders.pay_status='refunded'`
6. 返回 `SUCCESS / NOTFOUND / REPEATED`

#### D. 改造超时关闭任务

当前 `expireBooking()` 是本地直接：

- `status='cancelled'`
- `pay_status='expired'`
- 删除占房房态

改造后：

1. 先判断是否存在支付中台订单
2. 未支付时先调用 `/order/closeOrder`
3. 关单成功或已终态后，再更新本地状态
4. 释放房态

#### E. 改造用户取消接口

当前已支付订单取消会直接本地置 `refunded`

改造后应拆为：

- 未支付：先关单，再本地取消
- 已支付：发起原路退款，订单进入“退款中/已申请退款”，等待回调终态

#### F. 新增查询补偿逻辑

建议新增：

- `GET /api/juzhu/payment/query?order_no=...`
- `GET /api/juzhu/payment/refund/query?refund_order_no=...`

用途：

- 支付成功页兜底
- 订单页状态刷新
- 后台排查
- 定时补偿任务

### 15.2 前端

#### A. `lvju-app-pay.html`

当前：

- 进入页后查本地订单
- 点击“确认支付”直接调用本地 `/booking/pay`
- 成功后直接跳支付成功页

改造后：

1. 点击支付按钮调用改造后的 `/booking/pay`
2. 根据返回值处理：
   - H5 收银台 URL：跳转
   - SDK / 小程序参数：按端能力拉起
3. 从支付完成页返回后，不以本地跳转判成功，必须查订单或等回调结果

#### B. `lvju-app-paid.html`

当前：

- 只要进这个页面就展示“支付成功”

改造后：

1. 先查本地订单
2. 若本地还未到 `paid`，触发一次支付查询补偿
3. 未确认成功前只显示“支付结果确认中”

#### C. `lvju-app-orders.html` / `lvju-app-order-detail.html`

需要补充状态：

- `待支付`
- `支付中`
- `已支付`

- `已退款`
- `已过期`

#### D. `lvju-app-booking.html`

下单成功后跳支付页的链接建议补上支付单上下文参数，但不应直接把“去支付”视为必然成功。
