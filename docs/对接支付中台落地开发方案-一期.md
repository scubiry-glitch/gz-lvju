# 对接支付中台落地开发方案（一期）

## 1. 方案目标

本方案用于从零建设旅居民宿在线支付闭环，覆盖：

- OAuth 网关客户端封装。
- 支付中台接口封装。
- 贝壳用户身份关联。
- 支付下单、支付查询、异步通知和关单。
- 用户取消、商家取消、原路退款和退款查询。
- 支付及退款补偿任务。
- 前端收银台拉起和支付结果确认。
- 幂等、并发、安全、日志、监控和上线验证。

一期只处理 `booking_orders` 旅居民宿订单，不处理家政订单、部分退款、多次退款、独立分账接口和普通手机号用户支付。

## 2. 已确认业务规则

1. 在线支付只向贝壳登录用户开放，普通手机号用户暂不开放。
2. UCID 直接保存为 `accounts.idp_type='beike'`、`accounts.idp_subject=ucid`，不创建 `account_identities`。
3. `booking_orders.order_no` 作为合同号 `contractInfo.contractNo`。
4. 每次支付单号使用 `XD_yyyyMMddHHmmss_6位随机数字`，按 `Asia/Shanghai` 生成。
5. `jz_vendors.pay_merchant_no` 保存收款商户号；`shareBizCode` 使用环境统一配置。
6. `cashier_type` 由前端判断：App WebView 传 `"1"`，普通 H5 传 `"2"`。
7. 正常情况下每个预订单发起一笔支付；收银台过期但预订单仍有效时，旧支付明确关单后才允许生成新支付单。
8. 预订单过期后禁止继续支付，关闭未完成支付并释放库存；用户需重新创建预订单。
9. `booking_orders.paid_payment_order_id` 指向最终有效的支付记录，对应记录的 `app_order_id` 是有效支付单号。
10. 一期只支持整单、单次退款，但不对 `payment_refunds.payment_order_id` 设置数据库唯一约束，由服务层控制。
11. 重复支付或订单取消、过期后的晚到支付成功，自动创建原路退款单，同时记录异常并告警。
12. 支付、退款请求响应写网关日志；异步通知写通知日志，业务主表不重复保存响应原文和错误详情。

## 3. 总体架构

```text
浏览器/App
    |
    | 下单、查单、取消
    v
app.js 路由层
    |
    v
payment_service.cjs
    |-- 订单、支付、退款事务
    |-- 幂等与状态推进
    |-- 网关调用日志
    |-- 通知处理
    |-- 定时补偿
    |
    v
server/thirdApi/payCenter.cjs
    |-- 支付接口参数校验
    |-- 支付业务结果校验
    |
    v
server/utils/gateway-client.cjs
    |-- OAuth token
    |-- HMAC-SHA256 签名
    |-- Bearer 请求
    |-- 超时、重试、异常
    |
    v
支付中台
```

数据关系：

```text
booking_orders 1 --- N payment_orders
payment_orders 1 --- N payment_refunds
payment_orders/payment_refunds 1 --- N payment_gateway_logs
app_order_id 1 --- N payment_notify_log
```

支付中台 HTTP 调用不得放在数据库事务内。标准流程为：

1. 事务内锁定业务数据并保存待处理记录。
2. 提交事务。
3. 事务外调用支付中台并记录网关日志。
4. 新事务内推进本地状态。

## 6. OAuth 网关客户端

### 6.1 对外接口

```js
class GatewayClient {
  getToken(forceRefresh = false) {}
  buildPath(apiPath) {}
  fetch(path, options = {}) {}
  json(path, options = {}) {}
}

function createGatewayClient(options) {}
function buildOAuthSignature(path, method, params, secret) {}
function createNonce() {}
```

### 6.2 环境选择

统一归一化运行环境：

```text
production/prod -> prod
其他值          -> test
```

网关地址、客户端 ID、密钥和客户端类型全部从环境变量读取，不在源码提供真实默认密钥。`OAUTH_GATEWAY_URL` 必须可以独立覆盖默认地址。

### 6.3 Token 管理

- 使用 `client_credentials + HMAC-SHA256` 获取 access token。
- token 仅在进程内缓存。
- 在到期前 20% 时间窗口提前刷新。
- 使用 single-flight 合并并发 token 请求。
- 收到 token 失效错误时强制刷新并重试一次。
- 不向前端返回 token，不在日志、异常或数据库中保存 token。
- 多实例上线前确认支付网关是否允许多个实例共享或并行申请 token。

### 6.4 HTTP 请求

- 使用 Node 原生 `fetch`。
- GET 参数统一编码到 query string。
- POST 请求统一使用 `application/json`。
- 使用 `AbortController` 实现 token 请求和业务请求超时。
- 非 2xx 抛出 `GatewayHttpError`。
- 错误对象保存 `httpStatus`、`traceId`、脱敏后的原始响应。
- 业务层可同时取得解析结果和原始响应文本，便于日志留证。
- 不对 19 位 `orderId` 做数值计算，也不把它作为本地业务关联键。

### 6.5 网关单元测试

- `production` 和 `prod` 使用生产配置。
- 测试、开发和未知环境使用测试配置。
- 显式参数优先于环境配置。
- `OAUTH_GATEWAY_URL` 可单独覆盖。
- HMAC 签名参数排序稳定。
- 并发 token 请求只发起一次。
- token 失效只刷新重试一次。
- 请求超时抛结构化异常。
- 日志脱敏 access token、client secret、手机号和 UCID。

## 7. 支付中台接口封装

### 7.1 接口清单

| 方法 | HTTP | 路径 |
|---|---|---|
| `createC2BOrder(body)` | POST | `/pay/order/v2/createOrder` |
| `closeOrder(params)` | POST | `/pay/order/closeOrder` |
| `queryOrder(params)` | GET | `/pay/order/v2/query` |
| `refundOrder(body)` | POST | `/pay/order/refundOrder` |
| `queryRefundOrder(params)` | GET | `/pay/order/queryRefundOrder` |

一期不封装独立分账接口。

### 7.2 统一业务结果校验

HTTP 2xx 不等于支付业务成功。五个方法统一校验：

```text
Number(result.errno) === 0 && result.data != null
```

失败时抛出 `PayCenterBusinessError`：

```js
{
  name: 'PayCenterBusinessError',
  code: 'PAY_CENTER_BUSINESS_ERROR',
  errno,
  traceId,
  payResult
}
```

### 7.3 参数校验

- `appCode`、`projectCode` 分别读取，禁止混用。
- 下单校验 `appOrderId`、金额、用户、商户、收银台类型和分账明细。
- 查询和关单使用 `businessOrderNo=payment_orders.app_order_id`。
- 退款校验 `shareOrderInfos` 为非空数组。
- 金额统一使用两位小数的十进制字符串或 `DECIMAL`，禁止浮点累计。
- `cashierType` 只接受字符串 `"1"`、`"2"`。

## 8. 数据库迁移

新表使用 `CREATE TABLE IF NOT EXISTS`。存量表字段变更必须使用 `ALTER TABLE`，并追加到 `ensureSchema()` 的最后阶段，不得修改历史建表 SQL 或已经执行过的迁移清单。

### 8.1 商家收款配置

```sql
ALTER TABLE jz_vendors
  ADD COLUMN pay_merchant_no VARCHAR(64) NULL COMMENT '支付中台收款商户号';
```

业务下单按预订单所属商家读取 `pay_merchant_no`，未配置时禁止发起支付。

### 8.2 贝壳身份

第一期不创建 `account_identities`。贝壳登录按以下顺序处理：

1. 通过可信 `/token/verify` 获取 UCID。
2. 优先查询 `idp_type='beike' AND idp_subject=?`。
3. 未找到时按 `login_name='bk'+ucid` 查询存量账号并补齐身份字段。
4. 仍未找到时新建账号，同时写入 `idp_type='beike'`、`idp_subject=ucid`。
5. UCID 已绑定其他账号时禁止覆盖或自动合并，记录冲突并人工处理。

存量数据回填前必须先检查冲突，再执行：

```sql
UPDATE accounts
SET idp_type='beike', idp_subject=SUBSTRING(login_name, 3)
WHERE login_name REGEXP '^bk[0-9]+$'
  AND idp_type IS NULL
  AND idp_subject IS NULL;
```

## 9. 本地状态机

### 9.1 支付状态

| 状态 | 含义 |
|---|---|
| `creating` | 本地支付记录已创建，准备请求中台 |
| `paying` | 中台下单成功，等待支付结果 |
| `create_unknown` | 下单请求结果未知，只能查询补偿 |
| `paid` | 支付成功 |
| `pay_failed` | 支付失败 |
| `closing` | 正在关单 |
| `closed` | 关单成功 |
| `close_unknown` | 关单结果未知，只能查询补偿 |

允许 `pay_failed/closed -> paid`，用于处理中台晚到成功；禁止 `paid -> pay_failed/closed`。

### 9.2 退款状态

| 中台状态 | 本地状态 |
|---|---|
| `1/10/20` | `refunding` |
| `30` | `refunded` |
| `40/104` | `refund_failed` |
| `60/101/102/103` | `manual_review` |

### 9.3 订单摘要状态

```text
unpaid -> paying -> paid -> refunding -> refunded
                  \-> pay_failed
unpaid/paying -> closing -> unpaid
unpaid/paying -> closing -> closed/expired
```

## 10. 支付服务层

`payment_service.cjs` 通过依赖注入接收数据库连接创建函数、支付中台客户端、日志器和时钟，避免反向依赖 `app.js`。

建议导出：

```js
createOrReusePayment()
queryPayment()
markPaymentClosing()
closePaymentOrder()
createOrReuseRefund()
queryRefund()
handleNotify()
advancePaymentState()
advanceRefundState()
runPaymentCompensation()
runRefundCompensation()
```

所有金额、状态和业务归属校验集中在服务层，路由层只负责认证、参数读取和响应格式。

## 11. 支付下单

### 11.1 接口

```text
POST /api/juzhu/booking/pay
```

请求：

```json
{
  "order_no": "BKG-MINSU-00001",
  "contact_phone": "13800000000",
  "cashier_type": "1"
}
```

必须存在有效贝壳登录会话，并校验会话账号拥有该订单。前端金额不参与支付金额计算。

### 11.2 处理步骤

1. 事务内按 `order_no` 锁定 `booking_orders`。
2. 校验订单待支付、库存未过期、未设置 `paid_payment_order_id`。
3. 按 `biz_order_no`、`id DESC` 锁定最新支付记录。
4. `creating/create_unknown/paying` 时复用原记录，不创建新单。
5. `closing/close_unknown` 时返回关单处理中。
6. 仅最新记录不存在或为 `closed` 时创建新支付记录。
7. 从后端订单读取金额，从账号读取 UCID，从商家读取 `pay_merchant_no`。
8. 生成 `app_order_id` 并插入 `creating` 记录。
9. 提交事务后调用 `createC2BOrder()`，同时写网关日志。
10. 成功后更新为 `paying` 并保存收银台地址；不得直接更新为 `paid`。
11. 请求超时则更新为 `create_unknown`，查询原 `app_order_id`，不得换号重下。

### 11.3 下单字段映射

| 本地来源 | 中台字段 |
|---|---|
| `payment_orders.app_order_id` | `appOrderId` |
| `booking_orders.order_no` | `contractInfo.contractNo` |
| 项目名称及入住日期 | `appOrderName/tradeName/tradeDesc` |
| `payment_orders.amount` | `amount` |
| `payment_orders.merchant_no` | `recAndShareInfo.merchantNo` |
| `PAY_SHARE_BIZ_CODE` | `payChannel.shareBizCode` |
| 订单剩余有效秒数 | `payOrderInfo.expireTime` |
| 可信代理解析后的 IP | `appClientInfo.appClientIp` |
| `cashier_type` | `payChannel.cashierType` |
| `payer_ucid` | `userInfo.ucid` |
| `"2"` | `userInfo.userType` |

响应只返回业务所需的 `pay_status`、`cashier_type`、`cashier_url` 和有效期，不返回 OAuth token。

## 12. 支付查询与异步通知

### 12.1 主动查询

```text
POST /api/juzhu/payment/query
```

使用 `order_no + contact_phone` 并校验登录用户归属。默认查询该订单最新支付记录；客户端携带历史 `appOrderId` 时，只允许查询属于该订单的记录。

主动查询、异步通知和定时补偿必须调用相同的状态推进函数。

### 12.2 通知接口

```text
POST /api/juzhu/payment/notify/{PAY_NOTIFY_TOKEN}
```

该路由加入精确公开白名单，不能放开整个支付路径。处理步骤：

1. 获取原始请求体。
2. 验证支付侧约定的签名或来源校验。
3. 校验 `appCode/projectCode`。
4. 生成 `notify_key` 并插入通知日志。
5. 按 `appOrderId` 查找支付单或退款单。
6. 校验金额。
7. 事务内锁定支付/退款记录和业务订单。
8. 推进状态并提交事务。
9. 事务提交后发送商家通知。
10. 返回支付侧要求的纯文本。

| 场景 | 响应 |
|---|---|
| 首次处理成功 | `SUCCESS` |
| 本地单据不存在 | `NOTFOUND` |
| 通知或终态已处理 | `REPEATED` |
| 临时数据库异常 | HTTP 500 |

支付成功处理：

- 第一笔有效成功写入 `paid_payment_order_id`，更新订单支付摘要。
- 同一支付重复通知返回 `REPEATED`。
- 另一支付记录已成功时，为当前支付创建 `duplicate_pay` 自动退款并告警。
- 订单已取消、过期或库存已释放时，为当前支付创建 `late_pay` 自动退款并告警。

## 13. 关单和过期处理

关单使用：

```json
{
  "appCode": "lvju",
  "projectCode": "lvju",
  "businessOrderNo": "XD_20260916120001_123456",
  "ucid": "支付时 UCID",
  "userType": "2"
}
```

处理原则：

1. 事务内把未完成支付更新为 `closing`。
2. 事务外调用中台关单。
3. 成功后更新为 `closed`；结果未知则更新为 `close_unknown`。
4. `close_unknown` 未确认前不得创建新支付单或释放库存。
5. 收银台过期但预订单有效：关单成功后允许用户再次发起支付。
6. 预订单过期：关闭所有未完成支付并释放库存，不允许原订单继续支付。
7. 查询发现已支付时转支付成功流程，不得继续按过期单释放库存。

## 14. 取消和退款

取消入口：

- C 端 `/api/juzhu/booking/cancel`
- 商家端取消订单逻辑

未支付订单：

1. 锁定业务订单及最新支付记录。
2. 存在未完成支付时先关单。
3. 关单成功后取消订单并释放库存。

已支付订单：

1. 校验取消权限和免费取消政策。
2. 锁定有效支付记录。
3. 使用 `booking_cancel:{order_no}` 创建或复用退款记录。
4. 退款金额必须等于原支付金额。
5. 将原支付的 UCID、商户号复制到退款表。
6. 更新订单摘要为 `refunding` 并释放库存。
7. 事务外调用中台退款。
8. 等待退款通知或主动查询推进为 `refunded/refund_failed/manual_review`。

退款业务单号：

```text
RF + 业务订单号摘要 + yyyyMMddHHmmss
```

总长度不得超过 28。相同业务原因重试必须复用原退款记录和原退款业务单号。

## 15. 定时补偿

支付补偿扫描：

- `creating/create_unknown` 超过 10 秒。
- `paying` 超过 30 秒。
- `closing/close_unknown` 到达 `next_query_at`。

退款补偿扫描：

- `refunding/refund_failed/manual_review` 且到达 `next_retry_at`。

退避时间建议：`10s、30s、1m、3m、10m`。

多实例下使用条件更新抢占任务：

1. 查询一批到期记录。
2. 通过 `id + version + status` 条件更新取得处理权。
3. 事务外调用网关。
4. 新事务更新状态、重试次数和下次执行时间。
5. 达到上限后转人工处理并告警。

## 17. 安全和可观测性

- OAuth 密钥仅通过部署环境变量注入。
- 回调必须验签或执行支付侧认可的来源校验。
- 通知路径令牌只能作为附加保护。
- access token、client secret、手机号、UCID 和完整用户报文必须脱敏。
- 网关调用统一生成 `request_no`，保存 `trace_id`。
- 监控支付下单失败率、通知延迟、待补偿支付数、待补偿退款数和人工处理数。
- 重复支付、晚到成功、金额不一致、身份冲突必须产生告警。
- 公开路由只放行精确通知地址。
