# 券包功能优化计划（2026-10-07）

工作分支：`codex/coupon-functional-20261007`。本计划在隔离工作树实施，线上目录和服务不直接变更。

## 第一阶段：卡券可见性与状态

1. 增加本人卡券分页列表和按 ID 查询详情；列表使用稳定的订单时间排序，并返回各状态数量。保留现有 `/my` 响应以兼容旧调用。
2. 前端卡券列表、详情、会员中心与“我的”数量使用新接口。退款完成、冻结、过期、已核销分别显示；详情链接在超过 100 张券后仍能打开。
3. 验收：超过 100 张券可逐页查看；指定券详情可直接打开；退款成功后显示“已退款”，可用数量只统计未到期券。

## 第二阶段：销售与会员归属

1. 公开目录计算券包各组成 SKU 的可用库存，展示可购或缺货；会员卡片遵守真实购买和演示购买开关。
2. 本人会员记录返回所属城市与方案 ID；会员页按城市和方案 ID 判断“已开通”。
3. 验收：缺货时没有可执行购买按钮；关闭购买开关时不显示“立即开通”；不同城市同名方案不会互相标记为已购。

## 第三阶段：预约使用与景点入口

1. 预约日期按业务时区生成；线下券只在有效预约的服务当日展示可用核销码，并由服务端复核条件。
2. H5 景点页增加通往门票券目录的入口；已知城市时按城市筛选，未知城市时展示平台门票券，并明确适用范围以券详情为准。
3. 验收：预约日期与服务端一致；未预约或非服务当日不能取得可核销码；景点入口携带门票券分类，城市已知时携带城市。

## 验证与交付

优先运行针对性的接口和前端构建检查，再运行已有权益回归中受影响的用例。交付工作树路径、改动清单、通过项及未完成风险；部署另行审查。

## 后续功能待办

1. **景点与券适用关系**：当前景点只连到门票券分类；建立景点 ID 与 SKU 适用景点的结构化关联后，才能在景点详情直接展示可用券。验收时须检查跨城景点不会展示不适用商品。
2. **预约前的名额反馈**：当前用户选日期后才由服务端校验提前量、有效期和门店余量。增加可预约日期与余量查询，使日期控件提前禁用无效日期；提交时仍保留服务端原子校验。
3. **其他“我的”列表分页**：`/my` 的订单、预约、售后、会员等仍各限 100 条。按访问量和客服反馈逐项迁移到分页接口，保留旧接口兼容期。
4. **正式购买验收**：支付能力开启前，核对支付、库存预占、到账、退款与核销的完整链路，再开放真实购买入口。

## 第二轮推进（2026-10-08）

1. **景点匹配**：券商品配置增加分类与适用景点 ID；保存、审核、发布时校验景点启用状态、景区类型和城市归属。景点详情只展示已发布且明确关联本景点的门票券，并提供商品详情入口。跨市目的地允许显式关联；城市景点必须与商品同城。现有演示商品没有未经确认的自动关联，须由运营确认后配置并走复核发布。
2. **预约前反馈**：本人卡券增加可预约日期与余量接口，按北京时间、卡券有效期、门店提前预约时间和每日产能计算。预约窗口按 60 天浏览日期，已满或无效日期不可选择；提交仍由原预约事务再次校验并占用名额。
3. **列表分页**：本人订单、会员、预约、售后和核销记录有分页接口；售后将工单、退款与赔付合并分页。权益页订单、会员、预约、售后增加“加载更多”，订单详情按 ID 直接查询。主站订单中心按状态服务端分页，状态数量统计覆盖本人全部订单；旧 `/my` 仍兼容。
4. **正式购买准备度**：独立 MySQL 支付集成测试通过购买建单与库存预占、重复支付幂等、到账发券、部分退款、超时后晚到账退款、会员续期等 11 项。现网只读 `/api/commerce/v1/meta` 仍显示 `payment_enabled=false`。真实收单配置、机构回调与正式环境端到端验收尚未完成，因此本轮不开放真实购买、不部署线上。
