# 新居住统一分账系统设计

日期：2026-10-02。交付状态：可实施设计，未改业务代码、未执行迁移、未开启真实交易。

适用仓库：/proweb/run/sy。覆盖权益中心、生活服务站内贝壳收银台订单的真实分账，以及跳转外部小程序支付订单的正常出账、核对和下载；延续 Node + MySQL 和主站账号，从已有 commerce 结算实现抽出共享结算域，与[统一收银台设计](2026-10-02-unified-cashier-design.md)共同实施。保留原文件路径以兼容既有引用。文中的“新增”“改造”和状态名均为目标设计，不代表已经接通机构。

本版纳入三项明确需求：单笔分账可调整金额、付款时间和收款账户；所有收款方均可查看、下载本人／本主体对账单；按商户等规则选择自动结算或进入可配置人工审批节点后结算。对应详细设计见 §6.5—6.6、§9.1—9.3。

补充确定：**外部小程序支付也正常生成对账单**，不以是否使用本站收银台或是否具有本站分账能力作为出账条件。外部款项按实际证据展示交易、退款、合同应计及渠道结算情况，缺证据的条目照常列出并标待核验；不制造本站收款、可分余额或付款成功。完整流程见 §5.6、§8.5、§9.4。

## 1. 方案结论

采用“业务履约事件＋共享规则引擎＋按策略自动或人工审批＋机构资金执行＋收款方对账单”的架构。订单创建时锁定价格、费率、资金路线、履约确认与结算规则；站内支付成功确认可验证的资金来源，外部支付建立独立的交易证据关联。权益按券核销、生活服务按合同约定的履约确认产生应结。双周为现有权益默认账期，生活服务使用自己的合同账期；账单覆盖两种支付渠道，实际出金由资金能力决定。

受控代收资金模式的首期路线建议为两段：

1. **机构受控收款源 → 实际履约商户应结 S ＋ 平台佣金账户 B**。只释放达到本业务确认条件且取得有效执行授权的金额；授权可来自系统自动规则或人工审批。未核销券或尚未完成确认的服务对应资金继续保留。
2. **已到账的平台佣金 B → 推广结算 Q**，平台净留 N = B − Q。个人推广员通过完成准入的代发产品支付；企业渠道按其已批准收款关系结算。

比例模式下 S + B = A，B = Q + N。第二段以第一段的平台佣金入账为资金来源，不能再次扣用户原支付，也不能把 S、B、Q、N 四项一起下发。固定成本模式按 §3.2 仅释放 S、独立合同佣金 B 及其他获批用途，余额 U 继续保留。

如果机构确认支持同一原资金源直接向商户、企业渠道和平台分账，可启用单段 S + Q + N 路线。每笔计算锁定且只允许一种路线；路线切换只影响新计划，已有在途计划不能改道重付。

这里的“机构受控收款源”是**支付机构认可、完成授权的收款商户与合同资金账户**，不等于平台普通银行账户，也不等于券包里的第一家商户。实际服务销售主体、代收主体、平台和履约主体分别建模；系统不因统一收银台就把平台自动改成销售方。生活服务若由履约商户作为原收款人，按 §4.4 采用商户原款受控分账模式，不能机械再付一遍 S。

能够真实分账的完成标准是：一笔原支付能穿透到所属业务、订单、结算单位、履约确认、每方应结、每条机构分账／代发／回退流水和最终到账凭证；同一分钱的来源、用途、在途与退回均能解释。

### 1.1 本次覆盖范围与支付分流

| 业务 | 共享系统处理范围 | 业务确认单位 |
|---|---|---|
| 权益中心 commerce | 正式权益订单，真实原支付及其受控资金来源验证通过 | 单张券有效核销；会员专项权益按独立规则 |
| 生活服务 jiazheng | 原订单 payment_mode=pay_center，已由站内贝壳收银台确认支付，且结算合同与资金能力准入通过 | 首期为一张服务订单的有效履约确认 |
| 生活服务外部小程序 wechat_mini | 正常生成、查看和下载对账单；接收回传／导入证据并核对，外部收付仍由原渠道处理 | 外部订单与服务单位；有效合同和履约事实决定应计，交易及结算证据分别决定实收／已结 |
| 免费报修／咨询、售后镜像、演示或来源不明的旧单 | 不凭业务状态生成有资金的应付 | 有独立已到账补贴及批准规则的，应显式作为新的资助来源接入 |

支付选择仍按商家配置，不按品类推断。新订单由服务端读取商家 payment_mode 并锁定配置；是否可分账另外验证 settlement_profile。外部小程序订单不会因为商户后来切换 pay_center 就转成本地收款，原 pay_center 订单也不会因商户后来切回小程序而丢失存量查单、退款和结算能力。

出账采用独立能力维度：execution_scope=INTERNAL_FUNDED 为具备准入条件的站内资金执行；EXTERNAL_RECORD_ONLY 为外部交易记录、合同应计及对账。两者 statement_enabled 均为 true。未知／未匹配外部交易进入待核验清单，不转成站内支付；未开通出金、费率缺失或外部证据未到均不阻止已有订单出账。

### 1.2 五类规则分开配置

| 规则 | 回答的问题 | 两业务是否共享实现 |
|---|---|---|
| recognition_policy 履约确认 | 何时取得应结资格：券核销或服务确认 | 共享事件入口，条件由业务适配器提供 |
| allocation_policy 资金分配 | 哪一笔真实支付／补贴支持哪个结算单位 | 站内共享资金来源上限；外部仅分配证据及业务金额，不建立本站可支配来源 |
| calculation_rule 商业计算 | 商户应结、平台佣金、推广子佣金与费用如何计算 | 共享算法，按业务／商户／合同版本取参数 |
| execution_policy 结算执行 | 自动或人工节点、账期、付款时间、额度、账户 | 共享 §6 的调整、策略与授权；外部仅复核应计／证据，审批不能产生本站出金资格 |
| refund_policy 逆向处理 | 用户可退多少，各方承担多少，从哪笔原款退 | 共享资金执行，业务政策及责任分开 |

相同商户可以对权益采用一套佣金／账期，对生活服务采用另一套；共享引擎不意味着共用一组费率。AUTO 表示符合条件后的自动执行，不意味着付款成功就立即确认全部佣金。

statement_policy 单独控制出账周期、日期口径、字段模板、数据截止点及待核验展示，不决定资金归属。外部未约定专属账期时，采用默认自然月、北京时间半开区间 [月初,次月月初)；该默认只用于报表，不构成新的付款期限。站内继续按各业务合同账期。

### 1.3 共享边界与业务保留职责

共享核心接收业务事实及其证据，负责资金来源、分配、计算快照、应收应付、单笔调整、策略审批、机构执行、退款回退编排、账本和对账单。外部渠道记录明确保留证据等级，资金执行入口只接受 INTERNAL_FUNDED 上下文。它不创建券、不推进家政状态、不分配库存或档期、不解释用户评价。

权益适配器管理券、会员、预约、核销及到期政策；生活服务适配器管理商品价、派单、服务验收、取消和售后。两者通过持久事件和统一结算契约接入，不能为生活服务复制一套分账表或直接调用机构绕过授权。

~~~mermaid
flowchart LR
  P[站内贝壳收银台与公共支付核心] --> F[已确认资金来源]
  C[权益有效核销事件] --> CA[权益结算适配器]
  J[生活服务有效履约确认] --> JA[生活服务结算适配器]
  CA --> K[共享结算核心]
  JA --> K
  F --> K
  X[外部小程序交易回传或账单导入] --> V[外部证据核验与合同应计]
  V --> L
  K --> L
  K --> A[单笔调整与自动或人工授权]
  A --> E[机构分账 代发 回退 退款]
  E --> L[共享账本与各收款方对账单]
~~~

住宿现有收银台可继续使用公共支付核心，但本轮不将住宿分账纳入开发或验收范围。

### 2.2 审计基线与真实分账之间的差距

以下为本次开始审计时的代码基线（仓库 HEAD：cc8e116）。交付过程中发现共享工作区正在并行接入统一收银台：新增 commerce/payment-adapter.cjs、server/payment/ 等，真实建单已出现能力开关控制的适配入口，退款也在增加公共支付分支，结算增加了真实单禁止走沙箱的拦截。本设计未修改这些并行变更，也未将其视为已完成部署或机构验收；实施时以合并后的代码复核差距。下表用于说明改造缘由，不能当作收银台合并后的逐项完成状态。

| 现状证据 | 对真钱交易的影响 | 必须改造 |
|---|---|---|
| commerce/app.cjs 的真实 POST /orders 关闭，meta.payment_enabled=false | 尚无真实权益收款入口 | 按统一收银台方案接支付、可信回调、发券事件 |
| service.cjs 核销使用 floor 的比例分成 | 不能证明固定成本、补贴券和会员剩余资金已支持 | 增加互斥规则类型及资金来源分配 |

### 2.4 外部小程序订单的现有证据与改造缺口

外跳链路先由 [gr_orders.cjs](../../gr_orders.cjs) 创建 order_ref，记录 vendor_id、user_id、sku、biz_type=jiazheng 和 payment_mode=wechat_mini，再由生活服务路由传给商家。它与站内 jz_orders 是不同订单入口，共享上下文保留 source_order_system=gr_orders/jz_orders 和原 order_ref／订单号，不能要求外部单先有一张 jz_orders。

[商家回调实现](../../vendor_api.cjs)已有 HMAC 与商户归属检查；[回调协议](../../api_doc.md)的 vendor_oid 是商家业务订单号，fee 单位为分，均不等于机构支付流水。现有 completed 回调可跳过 paid，paid_at/completed_at 使用本地接收时刻，状态与金额也可能被后续回调覆盖。故历史 gr_orders 只作为候选事实，不能把当前 completed 或 fee 直接视作已核验支付、真实发生时间及最终结算。

现有协议没有完整退款流水、退款成功金额及时间，也未发现用于外部渠道的持久财务 Inbox、机构账单导入及人工证据复核闭环。客户订单列表还会隐藏外部 pending；账单读取原始业务表及新增证据表，不能沿用该展示过滤。上述缺口由 §5.6 补齐；不因此停止生成外部对账单。

## 3. 分账规则如何转成可执行规则

### 3.1 比例模式与按业务隔离的计算版本

所有金额使用整数分，比例使用基点，10000 = 100%。计算采用 BigInt 或受限整数库；数据库 BIGINT 和 JSON 金额统一以十进制字符串传输，禁止经过浮点元金额参与运算。

~~~text
A = 本业务结算单位锁定的结算基数
r = beike_bps
q = channel_bps
B = floor(A × r / 10000)                    贝壳佣金总额
S = A − B                                  商户应结
Q = 有有效推广归属 ? floor(B × q / 10000) : 0
N = B − Q                                  平台净留，尚未扣手续费等

必须满足：A = S + B；B = Q + N；A = S + Q + N
~~~

业务归属在下单时锁定。沿用现有签名来源验证、自购不计推广归属的实现；归属窗口、多人分享优先级等形成规则版本。没有归属时 Q=0，不生成“推广员 0 号”收款记录。

上式 FLOOR_BPS_V1 继承现有权益 MySQL 实现，避免用新算法重算旧券；M0 的 Math.round 结果不能迁入生产账。生活服务选择已审批的计算与舍入版本，不能直接调用按浮点元计算的旧工具或凭共享引擎静默改为 floor。新比例算法如有商务变更，另建版本。

生活服务费率配置可引用 vendor_rate.cjs 的商家差异化值→全局基准优先级，但须补已批准规则版本、合同引用、fee_source 和 rounding_policy，在下单锁定。缺少商家特定值时，只有经过审批且适用于该合同的全局规则才能生效；代码内置 10% 兜底不能单独放行真钱分账。权益 20%／渠道 50% 的演算参数不会自动带入生活服务。没有有效的生活服务推广归属及渠道协议时，Q=0。

商家佣金与家政服务者 L0—L7 收入分配是不同规则。本次先结算商家；若未来代付服务者，须明确从商家 S 或平台 B 的哪一部分支出并另获授权，不能给商家全额 S 后再从用户款重复支付服务者。

零金额组件保留计算结果但不生成零额分录或机构付款行；例如 r=0 时没有 B/Q/N 的出金，q=10000 时 N=0。现有 confirmLines 无条件写平台净留，而 post 要求正数，需要同步修正。各边界仍应满足守恒，不能以跳过零额行跳过规则校验。

### 3.2 固定成本模式：不能把余款全部当佣金

~~~text
S = fixed_cost_minor × 有效核销单位数
B = 按显式 beike_commission_rule 计算
Q、N = 从 B 中计算
F = 该券已获得的、可用于本次履约的资金
U = F − S − B − 其他经批准用途
要求 U >= 0；U 的用途必须单列，不能自动确认为平台收入
~~~

固定成本和比例模式互斥。固定成本是给商户的钱，OrderAllocation 是钱从哪里来，两者不是同一个字段。需求原文测试例：资金 40 元、固定商户款 30 元、合同佣金 10 元、渠道份额 50%，得到 30／5／5 元；这不意味着任何“会员费减商户成本”的余额都能被确认佣金。

### 3.3 分摊、会员和补贴

- 下单按已批准 allocation_policy 将资金分到**单张券实例单位**；同 SKU 两张券可以因尾差相差 1 分。先算全部整数份额，再按余数从大到小补分；同余按稳定 item_id + unit_sequence 排序。
- 多渠道受益人若启用，先确定本次可分的 Q 总额，再按权重分到子明细，采用同样最大余数法；单层推广是首期默认，不因数据结构预留就开放多级推广。
- 会员费允许拆为券资金、独立会员权益资金、尚未分配负债。后两部分有独立用途与退款规则，不能随一张赠券核销全部释放。
- 用户实付、平台补贴、机构采购到账、应收款、商户承担分别记录。未到账应收和未落实预算不进入可付资金；补贴核销或退款只能使用其已确认的来源。
- 未使用券到期自动建退款计划，按锁定的原支付分配退回付款来源。其他原因退款独立读 RefundPolicy；消费者可退金额不能笼统等同商户应结或结算基数。
- 机构采购折扣、渠道销售价差和推广佣金分列。对外支付额必须由实际到账及合同分配支持，不从券面额虚增。

### 3.4 规则快照及发布校验

每个业务结算单位至少引用：biz_type、订单与商品版本、供应商报价版本、资金分配版本、佣金版本、推广归属版本、舍入策略、履约确认政策、退款政策、账期政策、费用承担政策、资金路线版本。权益单位关联券，生活服务单位关联真实服务订单及确认事件。

发布校验覆盖：规则完整，金额非负，比例合法，资金覆盖，商户净结算不低于合同约定底价，加权佣金满足已批准下限，收款账户可用，机构支持券有效期内的分账和退款。

酒店通兑另校验“可选酒店 × 适用报价／成本规则 × 机构收款账户”全覆盖。预约时按购买时已允许的报价集合锁定实际酒店及报价版本；核销后不得换收款主体。若允许选店后产生差价，应有已批准补贴或独立尾款支付规则，不能临时从其他券资金补足。

以下完全沿用 v1.9 §6.2 的测试参数，不代表已经签约的费率；均为税费、支付费、代发费扣除前金额。

| 券 | 核销基数 A | 商户 S | 贝壳佣金 B | 渠道 Q | 平台净留 N |
|---|---:|---:|---:|---:|---:|
| A 保洁 | 199.80 | 159.84 | 39.96 | 19.98 | 19.98 |
| B 维修 | 133.20 | 106.56 | 26.64 | 13.32 | 13.32 |
| C 搬家 | 277.50 | 222.00 | 55.50 | 27.75 | 27.75 |
| D 旅居 | 333.00 | 266.40 | 66.60 | 33.30 | 33.30 |
| E 报告 | 55.50 | 44.40 | 11.10 | 5.55 | 5.55 |
| 合计 | 999.00 | 799.20 | 199.80 | 99.90 | 99.90 |

资金执行示例：五家商户分别收到 S；平台佣金账户收到 199.80；其中 99.90 保留为推广应付，由合格代发产品处理，余下 99.90 是平台业务净留。若平台账户与收款源相同，该步是机构确认的对应金额解冻／归属转换，不伪造向自己转账。

仅核销 A：最多释放 199.80 元，商户 159.84、贝壳佣金 39.96；未核销 799.20 元保留为负债。测试假设未核销券全额无手续费到期退回时，后者原路退款 799.20 元。首笔核销不能把剩余四张券资金一并解冻给平台。

没有推广归属、全部核销：商户合计仍为 799.20，平台净留为 199.80，不生成推广代发单。

### 3.6 生活服务演算与权益资金隔离

测试假设：站内付款 200.00 元，合同平台佣金 10%、无推广，服务达到确认条件后 A=200.00、S=180.00、B=N=20.00。10%仅为本例参数，不是生活服务默认合同承诺。

- 受控代收模式：机构向商户结算 180.00、向平台佣金账户划入 20.00。
- 商户原款受控模式：原款已在商户机构账户但尚受控，机构释放／确认其 180.00，并从该原款向平台划入 20.00；不能另向商户再付 180.00。
- 若另有有效推广协议约定 Q 为 B 的 30%，则 Q=6.00、N=14.00；Q 从已到账 B 支出，仍然是 200.00=180.00+6.00+14.00。此值也仅用于验算。
- 服务未达到确认条件，200.00 记录为对应业务的待履约资金／负债，不因付款成功就发出上述结算。

同一商户同时有权益 A 券和这张服务单时，账单可分别列出商户应结 159.84 与 180.00，合计 339.84；执行仍保留各自原支付、合同和费率，不能用一个来源的钱支付两笔。若商家收款模式不支持保持受控或后续分账，该订单不按本例伪造机构余额。

## 4. 收款账户、账务账户与真实资金路线

### 4.1 主体与账户

| 对象 | 需要保存 | 容易混淆的边界 |
|---|---|---|
| 用户原支付 | payment_id、机构交易号、实付额、付款来源引用、币种 | 退款退原支付，不退当前券使用人的任意银行卡 |
| 权益收款主体 | legal_entity_id、collector_entity_id、provider_merchant_no、支付合同版本 | 与服务销售方可以不同，但必须有机构认可的代收关系 |
| 实际履约商户 | merchant_id、legal_entity_id、收款账户版本、merchantNo、可接收合同 | 不是登录账号 ID，也不一定是发券锚点商户 |
| 平台佣金收款主体 | 独立账户版本、merchantNo、合同授权、费用承担方 | 佣金 B 内含推广应付 Q，不能把 B 全部视为可自由支出的 N |
| 推广受益人 | 个人／企业类型、实名和结算资质引用、代发接收方 token、税费政策版本 | 不把普通 accounts.id 当作支付机构商户号 |
| 平台赔付资金 | 机构侧独立账户／产品、可用余额凭证、预算版本 | 与用户未核销资金物理分离 |

银行账号等敏感资料仅保存受控引用和必要加密数据；页面只显示掩码，审计不写明文凭据。密钥沿用宿主凭据机制。

账户资料变更形成新版本并走账户准入审批；它与某笔分账是否人工审核分开。单笔可选择同一合法收款主体已审核、通道可用的其他账户，具体规则见 §6.5。已授权但未发送的资金单修改后重新产生授权；已发送或在途的资金单固定原版本。不得对同一个机构幂等号替换收款人或金额。

### 4.2 推荐流程

~~~mermaid
flowchart TD
  A[用户支付] --> B[支付中台确认收款]
  B --> C[机构中原支付及合同资金来源]
  B --> D[收款事件入账并发券]
  D --> E[真实核销和逐券计算]
  E --> F[商户与平台佣金应结]
  E --> G[推广佣金应付]
  F --> H[结算策略判定：自动授权或人工审批]
  H --> I[按原支付与合同编排分账子单]
  C --> I
  I --> J[商户机构账户入账]
  I --> K[平台佣金账户入账 B]
  G --> L[推广结算策略授权及资金校验]
  K --> L
  L --> M[机构代发及逐人结果]
  J --> N[银行结算凭证]
  M --> O[推广实际到账与税费凭证]
  C --> P[未核销原路退款]
  I --> Q[回退与退款编排]
~~~

“商户机构账户入账”“银行结算中”“银行到账”分开显示。接口只返回分账成功时，不能直接展示银行卡已到账。代发总批次完成也不能替代逐个推广员的结果。

### 4.3 机构能力不满足时的确定处理

必须验证跨商户收款关系、分账可用期限、资金留存方式、接收方限额和分账比例上限。长有效期权益不能默认套用短期交易分账冻结功能。

例如微信支付公开文档说明其特定分账产品存在冻结期限、可分金额、接收方提现及回退限制，这说明上述限制必须按**实际产品**核实；不能把微信参数直接当作本项目 ACN 的参数。[微信支付分账常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4014547102)

若当前支付产品不能支持券有效期内资金控制及原路退款，本商品保持不可售，改用机构明确支持的合同账户产品，或经业务批准调整商品期限。不可通过平台普通账户先收全款再私下付款来补接口缺口。单商户短期券只有自己的能力项全部通过，才可单独进入试点，不能替代多商户券包验收。

### 4.4 生活服务原商户收款与防重复结算

payment_mode 只决定收银台路径，funding_mode 决定如何实际清分。新订单支付创建之前，必须锁定已准入的 settlement_profile，包含实际收款主体、资金控制产品、合同版本、商户分账授权、费率快照和可分／可退期限；支付请求由该快照生成，不能付款后才发现原款已经不可分。

| funding_mode | 原款状态 | 共享核心如何执行 |
|---|---|---|
| CONTROLLED_COLLECTION | 款在机构认可的代收合同账户，未分给履约商户 | 按 S、B 或 S、Q、N 向各方执行机构划转 |
| MERCHANT_CONTROLLED_RECEIPT | 原收款人就是履约商户，原款在其机构账户仍受控 | S 为商户原款保留／释放，不新增对商户的转账；B 从该原款分给平台。若机构提供分账同时释放剩余资金，按其真实结果记录 S 释放 |
| MERCHANT_ALREADY_SETTLED | 原款已全部归商户可支配或已银行结算 | 不重建 S 待付款；只有已批准的商户资金分账／扣款产品和证据才能执行 B。缺此能力仅登记待核验的佣金应收，另行收取的产品流程不在本次自动分账范围 |
| UNVERIFIED | 无法确定资金归属、控制或既付额 | 可展示带状态的业务应计，禁止生成可出金计划 |

优先让新接入站内收银台的生活服务商家使用符合其合同的 MERCHANT_CONTROLLED_RECEIPT；如果机构产品要求代收主体，则明确采用 CONTROLLED_COLLECTION。两种模式共用规则、授权与对账，不能由“资金金额看起来够”自动互换。

商户释放 S 记为 MERCHANT_RELEASE 资金事实，由机构释放结果／交易账单确认，不能制造“付款方=收款方”的假转账请求。原支付来源的 S+B 上限仍成立，但仅 B 产生向平台的外部划转；商户原款控制解除和银行卡到账分层展示。机构若不支持逐单位部分释放，不为同一原支付开放多阶段结算。

机构动作的隐含效果同样受授权约束：如果划转 B 会自动释放剩余 S，执行计划必须同时包含全部实际释放额，并取得 S、B 各自有效授权，且都已到执行时间、没有冻结。S 人工待审、暂缓、改期或只批准本次部分付款时，不得单独发送会释放全部 S 的 B 请求；界面显示所依赖的未满足条件。只有机构已证明支持独立部分释放及保留余款，才允许分开执行。请求中的显式划转与隐含释放作为不同效果行记录，隐含行由同一机构请求结果驱动，不再发送第二条释放请求。

MERCHANT_RELEASE 的 S 同时计入商户已清偿额和原资金已消耗额，与实际向商户划转一样消耗原授权；不能因解除机构控制而恢复为平台可分余额。撤销尚未执行计划产生的 reservation_released_minor 仅撤销本地预占，向商户释放原款产生的 merchant_released_minor 则永久保留清偿历史；两者字段、事件和余额处理分开。

历史 pay_center 订单接入时，先逐笔核验原支付、原合同、实际既付／已释放额、历史退款、应计佣金与剩余可分额，形成唯一导入事件和审批证据。已经付给商户的款不能再次作为 S 待付导入；缺原费率和资金证据的只列待核验。商户新配置只影响新订单，不能用新费率追算旧单。

### 4.5 外部渠道的资金与出账边界

wechat_mini 上下文固定 execution_scope=EXTERNAL_RECORD_ONLY，funding_mode 不映射成任何可出金模式；支付证据可核验，但本站没有因此获得原款控制权。外部交易、商户经济净额、平台佣金应收均可以出账；不为这些交易创建站内 funding_sources、用户资金负债、MERCHANT_RELEASE 或 execution_orders。

外部的“已支付”“已退款”“渠道已结算”“平台佣金已收”分别由对应证据确定；商户签名回传只证明报送方身份，不能单凭签名把商户报送升级为支付机构确认。合同存在平台佣金应收时明确债务人、债权人和履约条件；商户经济净额不是本站欠商户的应付。

外部账单被确认、人工审批通过或规则命中 AUTO，均不能改变其执行范围。若后续外部佣金确实汇入平台，只凭已到账流水销减应收；相关平台自有款或佣金款后续出金需作为独立资金来源另行准入，不能将原外部消费者交易转为站内可分本金。本轮实现外部账单及实际清偿记录，不新增外部渠道代扣、付款或退款接口。

## 5. 模块与数据模型

### 5.1 模块职责

从现有 commerce/settlement.cjs 抽取 server/settlement/ 共享模块。commerce/settlement.cjs 保留为权益兼容入口，调用共享核心；生活服务增加 jiazheng 结算适配器，调用同一个核心。两业务均不得直接操作机构资金或另记一套结算账，保留“一个资金事实只有一个写入者”的原则。

| 模块 | 目标职责 |
|---|---|
| 统一支付核心 | 支付尝试、原支付退款、回调验证、查单、持久任务；复用现有 payment_orders/payment_refunds |
| commerce/service.cjs 与权益结算适配器 | 权益订单、发券、核销及到期；输出可信结算事件和券政策，不负责机构报文 |
| 生活服务结算适配器 | jz_orders 支付与履约确认、服务退款政策、资金分配及费率快照；按原 payment_mode 进入站内执行或外部对账，不生成虚拟券或伪核销 |
| 外部交易对账适配器 | 商户回传、授权查询、文件导入、交易关联、证据核验及外部结算映射；调用共享账单模块，不调用站内付款／退款 worker |
| commerce/settlement.cjs | 旧权益 API 的兼容门面，转入共享核心；不保留一份独立资金算法 |
| server/settlement/ 共享核心 | 两业务统一应收应付、调整、规则授权、执行、账务、逆向、对账和收款方账单；账单覆盖站内与外部渠道 |
| 内部 calculation 模块 | 纯函数计算和不变量；不读当前费率，不发网络请求 |
| 内部 execution-planner 模块 | 将获批应结编译成受来源与合同约束的资金子单 |
| 内部机构适配器 | PayCenter 分账、回退、查单；独立代发／结算／账单适配 |
| 持久 worker | Outbox、Inbox、租约、重试、对账下载和异常恢复 |

补充数据库约束：

1. 同一执行组件的历史清偿额（成功划转＋商户原款释放）＋活动支付占用＋已生效及活动抵扣，不超过该组件批准额度减去其已取消未付部分；调增创建独立补差组件。义务层再汇总所有组件，校验累计消耗≤原批准额度＋已生效补差−已取消未付额度，两层同时成立。已清偿后的业务冲回转为应收追偿，不清零原成功，也不重新开放原组件额度。机构真实预占另存凭证，本地排他占用不能冒充机构冻结。
2. 相同来源的所有机构资金流、退款、在途占用与可用额按机构口径守恒；source→平台 B→推广 Q 属于两跳，禁止将二者重复累计为原支付流出。
3. 唯一(provider, environment, operation, request_no)；唯一(provider, environment, provider_transaction_id, provider_line_id, event_kind)。金额和收款参数受 payload_hash 保护。
4. 一张财务批次可映射多个执行单；一个同源执行单可承载多个批次已经自动／人工授权的行。执行行必须能反查各自授权版本；不能按批次总额取代原支付来源。
5. 部分重试复用同一逻辑行和原请求；若机构只能将终态失败原单永久封存，新指令必须经受控“替代计划”审批，记录 supersedes_id，原单查明确实不可再成功并释放占用。默认沿用原号，UNKNOWN 永远不走替代流程。
6. 历史订单／券快照、分录和已执行计划只读；迁移使用新版本号，不修改已有 004/005 checksum。
7. 外部订单、交易证据和已确认合同应计可以生成账单；只有 INTERNAL_FUNDED 且 funding_source/授权匹配的组件才可编译出金。站内执行相关非空约束不适用于外部候选账单行，不能以伪造支付号绕过。

上述 id 默认 BIGINT 或既有业务 UUID；实收、付款、退款和分录金额使用非负 BIGINT，调整 delta_minor 为有符号 BIGINT，也可用 direction + 非负 amount 表示，生效后逐组件余额须合法。币种 CHAR(3)，环境、operation 和状态枚举受服务端校验；外部号长度以实际契约确定，不截断。执行明细外键连接原计算、原分账行、资金来源及授权版本；事件／请求唯一索引之外，还需通过锁定来源控制行后条件更新，约束累计成功、活动支付及抵扣占用。CHECK 不能代替事务并发控制。

平台佣金 lot 以实际入账行而非平台账户总余额划分。首期要求该计算对应 B 足额、可用且无退款冻结后才放行 Q；B 部分到账、在途或被冻结时不全额放行 Q。已有 B 的资产转移不重复确认收入。平台提现只使用扣除 Q 专用占用、税费与已批准逆向准备后的 N 可用部分。

### 5.3 支付标识兼容

沿用统一收银台已经确定的边界：payment_orders/payment_refunds 的 biz_order_no 保持 VARCHAR(32)，权益 UUID 仅在适配层无损去连字符；biz_type + biz_order_no 为非唯一历史索引。业务 UUID、支付尝试号、分账请求号和机构流水号分别保存，不互相代用。

共享结算以 biz_type + source_order_system + 业务原号建立上下文；权益保留完整 UUID，站内生活服务保留 WO-… 原号，外部保留 gr_orders.order_ref。同一真实订单在 jz_orders 与 gr_orders 的展示投影通过明确映射归一，不能各认定一次。支付表的 32 位标准化标识另存引用，不为了共享而扩容支付订单号或截断原业务主键；外部 vendor_oid、机构交易号、退款号各自独立保存。

### 5.4 两业务接入契约与幂等边界

业务适配器经内部调用或验签事件提供以下内容；共享核心按 execution_scope 分流，自行验证证据和来源，不接受浏览器直接宣布支付成功或可结算：

~~~text
SettlementContext
  biz_type: commerce | jiazheng
  source_order_system / biz_order_no / settlement_unit_key / event_producer / source_event_id / event_version
  payment_mode / execution_scope / statement_policy_version
  INTERNAL_FUNDED: funding_mode / accepted_payment_id / funding_allocation_ids
  EXTERNAL_RECORD_ONLY: external_order_link_id / external_evidence_refs / verification_status
  seller_party_id / collector_party_id / fulfillment_party_id
  approved_rule_snapshot_id / recognition_policy_version / refund_policy_version
  recognition_evidence_ref / confirmed_at / available_at / dispute_flags
~~~

适配器提供 resolveContext、validateEligibility、resolveCalculationInputs、quoteRefund、applyBusinessResult 五类能力；外部另提供 ingestEvidence、resolveExternalFacts、buildStatementInputs。站内公共支付核心负责原支付／原路退款，共享结算核心负责分账／回退及应付；站内退款只能有一个 payment_refund_id。外部使用真实 external_refund_id 及证据关联，不伪造 payment_orders/payment_refunds 记录来满足旧约束。

站内支付成功先按唯一(provider,environment,payment_id) 入账并分到对应业务的待履约负债；消费者按不同业务投影处理发券或派单。payment.received、payment.accepted、回调和查单可能描述同一资金事实，不能各记一次收款。未被订单接受的重复／迟到支付只进入待退款来源，不得支持结算。外部支付成功只形成外部交易事实，按 §8.5 处理合同应计，不贷记本站用户待履约负债或创建本站资金。

同一业务事实按(business_context_id,event_producer,source_event_id,event_version) 去重，生产方命名空间由适配器固定；同时约束每个 settlement_unit_id 最多一份有效确认计算，防止把 done 和 rated 两个不同事件各结算一次。业务撤销和重建引用原 recognition_id，以明确修订处理，不通过换事件号重复认领整单金额。

服务完成、退款申请和出金授权共享来源锁与版本仲裁；同库时业务事实及 Outbox 在本地事务提交，异库通过可重放的 Outbox/Inbox 交付。业务投影失败只重试状态同步，不重付、不重新生成应结。

### 5.5 生活服务履约确认与逆向适配

首期普通服务一单一个结算单位。支付成功仅允许进入后续服务流程；派单、接单、服务中、商家声明完成和客户评价均不直接执行资金分账。

推荐履约规则为“商家提交完成凭证→客户确认验收→共享核心确认应结”。如合同明确支持自动确认，可配置告知后的验收窗口，窗口届满且无阻断售后时由任务产生确认事件；窗口时长不硬编码。现有页面与服务端尚无这套确认事实时需补接口及证据，不能把 done 或五星评价当作客户验收，也不能把不评价视为不结款。

站内服务认定已满足履约要求后，适配器核验已接受支付、原规则、实际服务商、有效单位、无退款／争议冻结及资金来源，输出 settlement.eligible；共享核心计算并走 AUTO 或 REVIEW，再到约定时间执行。外部服务按相同合同确认语义产生 external.accrual_eligible，仅驱动应计与账单，不进入出金队列。关闭自动销售不影响存量售后与原单查询。

部分履约、定金／尾款和分阶段服务，须另外审批单位拆分和资金分配规则，关联每笔实际收款后才启用；首期不因为支付表允许多次尝试就将其当作多笔有效付款。多次尝试只有 guard 接受的有效支付进入资金来源，其余仍按重复款处理。

生活服务取消与退款采用服务合同：派单前可沿当前规则全额原路退；派单后、已完成或部分履约需独立售后政策与批准金额。共享退款计划按原支付和服务单位分配，补齐部分退款累计额度、已分账回退和账户资金不足路径；不套用权益到期退券规则。

权益券履约关联 jz_orders 时，该服务单只是履约载体：其资金仍归 commerce 券来源，在有效核销时认定一次。权益售后镜像、免费工单不能被 jiazheng 适配器再次确认为现金订单。有独立站内尾款时，只对确实支付的尾款单位另行认定，记录券抵扣与尾款的资金覆盖，防止按服务原价重复结算。

### 5.6 外部交易接入、核验与正常出账

外部适配器从 gr_orders 读取本主体 biz_type=jiazheng AND payment_mode=wechat_mini 的全部订单（包括 pending），结合 vendor_id、order_ref 和审核后的 party 绑定建立上下文。支付模式缺失的历史记录先列待分类；pay_center 与 commerce 展示投影只做原业务别名映射，不建立外部上下文。跳转意图本身进入订单覆盖清单，状态为待支付／支付未确认，不能视为交易发生；不受消费者列表隐藏 pending 的逻辑影响。渠道仅回传商家订单号或导入有流水但无本地订单时，保留在该商户待匹配清单，经证据关联或受控历史补录后归属；不能凭同金额、手机号或相似名称自动认领。

| 接入途径 | 处理与证据含义 |
|---|---|
| 商家签名回传 | 校验签名、商户身份、时间窗、事件号及原单归属；先持久 Inbox 再应答。记 MERCHANT_REPORTED，不能直接记机构已核验 |
| 经授权服务端查询／渠道交易接口 | 保存请求关联、响应摘要、查询时间和能力版本；按实际来源区分商家查询或支付机构查询，不凭接口成功码判断资金状态 |
| 商户或财务导入账单 | 使用版本化 CSV/XLSX 模板，金额及单位、币种、交易号、日期、方向逐行校验；预览新增／重复／冲突／未匹配结果，复核后发布入库。文件原件、hash、错误行和重复行均保留 |
| 人工补证／历史补录 | 记录申请人、原件引用、事实范围与独立复核人；通过后记 MANUALLY_VERIFIED，并展示人工核验来源，不冒充机构自动验真 |

外部事件至少保存：外部渠道与环境、商户账号、order_ref/vendor_oid、event_id、event_kind、transaction_id/refund_id/settlement_id、关联原交易、gross/fee/net 金额及明确单位、currency、occurred_at、received_at、verified_at、evidence_ref/hash、schema_version、原报文受控引用。支付、履约、退款、渠道结算与平台佣金到账分别有事件和状态，cancelled 不等同退款成功，completed 不补造支付事实。

缺机构交易号的商家回传仍可持久记录，以可信商户事件号防重，并以订单＋事件语义＋业务修订归并候选事实；旧协议无事件号时用规范化载荷 hash 去重相同报送，发生内容变化视为冲突／更正候选，不能当作第二笔收款。取得真实交易号后建立证据别名映射，归入同一规范事实，不重复计款。

已知交易按(channel,environment,external_merchant_account,event_kind,external_transaction_id)唯一归并，退款号及结算号使用各自类型的键。回传与文件导入是同一事实的多个证据，不是两笔交易；文件 hash 只防同文件重传，跨文件仍逐交易去重。不同号实际重复付款保留原始流水并列异常，同一业务单位只产生一份合同应计。

事件关联表支持一笔支付对应多个单位、多个退款对应一笔原支付、一次结算对应多个订单／账期。allocation_purpose=BILLING_BASIS 的计费依据分配受合同批准采用的基数上限约束，可引用满足证据政策的商家报送，保留其待核对状态；VERIFIED_CASH 的收付分配才受已核验资金事实金额上限约束。两类分配是同一事实的不同用途，不能相加成交易总额或同一佣金的两份计费基数。批量佣金到账需要匹配明细或经复核的分配单，不能给每张订单都记整笔到账。累计外部退款超原款、币种冲突或报文金额修正须列差异，不自动净额抵销。

补证升级原规范事实及其分配版本；原先已获准确认的应计金额不变时只更新证据引用，金额或合同条件改变才追加批准差额，不新记整笔应计。BILLING_BASIS 的存在不生成已核验实收；原事件在两个用途中的分配分别防超限且保留关联。

候选金额、币种和发生时间可为空；原始值与标准化值分开，未知不写 0、不默认沿用商品售价或当前费率。已知金额用整数分或币种规定的最小单位，禁止浮点累加。金额／币种未知的记录进入未知金额或待匹配币种附表，不能混入某币种合计。原 schema 对可执行金额的非空约束只约束站内资金指令。

核验状态按事实分别保存 REPORTED、PENDING_EVIDENCE、VERIFIED、CONFLICT，并另记 evidence_source=MERCHANT_REPORT/PROVIDER_QUERY/PROVIDER_STATEMENT/MANUAL_REVIEW。可信商家报送也可按已批准的证据政策形成合同应计，但其支付机构核对状态仍独立为待核对；不能把“应计已确认”写成“银行已到账”。需人工复核的材料由非提交人审核，任一来源冲突进入差异队列，保留事实版本，不简单以最后到达者覆盖。

账单生成只需要可归属的业务订单或受控补录事实，不等待核验全部完成。站内和外部均由同一 statement_generator 从冻结的数据截止点与版本生成；出账任务不依赖 settlement_batches 已生成、不要求应付或付款授权存在。订单、核验和合同应计分别引用源事件，账单异议及人工更正复用原有调整与审计流程。

## 6. 结算策略、单笔调整与实际资金指令

### 6.1 业务账期与权益双周日历

引入 settlement_policy：biz_type、合同范围、timezone=Asia/Shanghai、anchor_date、周期、period_end、review_deadline、执行窗口、节假日处理。权益默认周期 14 天，生活服务按其合同配置；anchor_date 和到账 SLA 由合同确定，不擅自把“双周”解释成“每月 1—15 日及月底”。

账期采用半开区间 [start_at,end_at)，存 UTC，展示北京时间；按各业务有效确认时间归期，权益为核销确认，生活服务为其履约确认。正常明细按合同默认执行窗口付款，也可按 §6.5 调整单笔计划时间；账期归属、计划发起时间与实际到账时间分别保存。明确争议项单列冻结原因、责任人及处置时限，不能以全批不结掩盖单项异常。

系统可每天对账、在账期末完成正式核对。“当期差异处理完”指定位、解释并记录状态；机构尚未给出结果的 UNKNOWN 保留在途，不为平账改成成功或挪至下期重新付款。

### 6.2 统一执行授权与不可变版本

本节资金状态机只用于 INTERNAL_FUNDED。外部应计调整、账单确认和证据复核使用 purpose=EXTERNAL_ACCRUAL/STATEMENT_CONFIRMATION/EVIDENCE_REVIEW 的审批实例，不能签发 purpose=FUND_EXECUTION 的授权；外部对账仍按 §9 的出账及核验状态推进。

~~~text
DRAFT → EVALUATING
          ├→ AUTO 条件通过 → AUTHORIZED
          ├→ REVIEW → IN_REVIEW → 全部必需节点通过 → AUTHORIZED
          │                    └→ REJECTED / RETURNED_TO_DRAFT
          └→ 条件不满足 → BLOCKED
AUTHORIZED → WAITING_SCHEDULE → READY → EXECUTING
                                         ├→ PARTIALLY_COMPLETED
                                         ├→ COMPLETED
                                         └→ EXCEPTION
~~~

上述是结算授权与业务执行状态，不取代 §6.4 的机构指令状态。授权按具体收款组件／付款安排发放，账期批次只聚合展示。同批次可同时存在自动授权、人工待审、定时待付和已付明细，不因一条待审就阻断其他独立获授权明细；共享原资金或两段路线依赖仍须满足。

提交即冻结 revision 内容。authorization_hash（兼容旧设计 approval_hash）覆盖明细 ID、计算及调整快照、金额、计划付款时间、收款账户版本、合同与机构能力版本、资金路线及机构隐含释放效果、结算策略／审批模板版本、退款政策、费用与抵扣、币种、账期。AUTO 保存系统判定证据，WORKFLOW 保存逐节点审批记录；二者均生成持久执行授权，不要求自动路径另点一次人工确认。

任何实质变更使受影响授权失效，产生新 revision 并重新评估策略；需要人工的再审，需要自动的重新执行规则并留痕。若一份审批实例包含多条明细，实例内版本变化使整份实例失效；其他独立授权不受影响。批量操作可逐项通过，不允许用总批次已审批代替子项授权。

冻结执行只禁止尚未发送的指令，不表示撤回已发送资金。执行中原请求仍要查单、接回调；只有机构确认撤销或失败，才允许释放相应占用。

迟到核销／补录不能改写已经定版的账单。形成同账期调整批次，链接原批次与独立修订号，再按策略授权；每条有效计算组件仍只能在其额度内结算。

单次付款执行完成不等于整笔业务应付结清。存在分次付款余款、暂缓金额或尚未完成的审批时，业务明细与批次保持 PARTIALLY_COMPLETED／待结清，分别展示本次执行结果和累计结清进度。

### 6.3 指令编排

~~~text
输入：AUTHORIZED 且 hash 一致、已到计划付款时间的明细
0. 必须为 INTERNAL_FUNDED 且授权 purpose=FUND_EXECUTION；外部对账组件返回 EXECUTION_SCOPE_DENIED，不创建指令或资金占用。
1. 锁账单修订、来源资金控制记录、明细占用、追偿分配。
2. 校验业务上下文、原 payment_mode/funding_mode、有效履约确认、授权、单笔计划、真实支付及到账资金、收款资质、退款冻结和演示隔离。
3. 按 provider + environment + currency + source_account_version
   + funding_mode + payment_contract_version + source_payment_id 分组。
4. 展开机构动作的全部显式划转及隐含释放效果，逐一验证授权、时间及冻结状态；任何必然发生的效果不满足条件则不发该请求。只合并授权有效且执行窗口兼容的行，在机构限制内生成不可变 execution_order/lines。
5. 同事务创建本地排他占用及 Outbox；提交事务。
6. worker 原子校验当前授权／计划版本及到期时间，READY→SUBMITTING 后事务外请求机构。
7. 响应/回调持久化 Inbox，经核验后逐行推进；机构实际预占或出金另记镜像。
8. 各行终态汇总到计划、批次；跨合同、跨账户不得合并成一个请求。
~~~

付款、退款、撤销共享原支付／合同的资金控制锁。与公共收银台统一锁顺序为支付 guard → 所属业务订单 → payment_orders → payment_refunds → 来源控制行 → 业务资源（券／库存／档期）→ 结算单位及计算组件 → 批次修订 → 执行行 → 追偿；各组按稳定 ID 排序，只取所需锁，不持有任务租约行锁等待上述事务。死锁重试沿用原幂等键，机构调用在事务外。机构提交还须具备原子扣减／预占或不超原单余额的机制；查询一次余额不能代替机构防超付。

如机构只支持合同余额而非原支付级 split，允许在适配层按其契约聚合，但平台 execution_allocations 必须继续保留逐原支付、逐券来源，且要验证原路退款能力。首期不在无证据时启用这种聚合。

多来源资金另读 funding_use_policy，逐用途指定哪些来源可付商户 S、平台 B、推广 Q，以及退款顺序。补贴款不自动并入原收单交易可分余额，需要机构支持的补差／独立付款路径及关联来源证据。

### 6.4 状态、幂等与 UNKNOWN

| 状态 | 判定 | 允许动作 |
|---|---|---|
| READY | 指令落库，未发请求 | 校验后发送；未发送可撤销 |
| SUBMITTING / PROCESSING | 已发请求，机构处理中 | 接回调、查原请求 |
| UNKNOWN | 超时、断链、无法证明未受理 | 持续占用，只查原请求；告警并升级处理 |
| PARTIAL | 部分接收行成功，部分仍未终结或失败 | 已成功行不可重发；其他行按各自状态处理 |
| SUCCEEDED | 机构确认到达该 operation 的成功终态 | 幂等记账并保留流水，不允许回退状态 |
| FAILED_FINAL | 机构明确终态失败且无扣款／占用已释放证据 | 按契约受控重试或替代审批；不按 HTTP 错误自行判定 |
| CANCELLED | 未发送本地取消，或机构确认撤销 | 释放对应控制占用并记审计 |

业务受理成功码仅代表“已受理”，不等于每个收款方成功。批次 COMPLETED 需所有应付行成功、或有经批准的有效抵扣／冲回，且无在途；不能只看一个总单 paid。

Outbox worker 使用数据库租约、attempt 序号和唯一任务键。进程在“机构已受理、本地尚未记结果”时崩溃，恢复后以原请求号查单；绝不重新生成请求号。

回调验签／可信来源、金额、币种、合同、源账户、收款账户、请求与明细号均从本地快照核对。重复回调返回幂等结果；冲突终态保留证据并以机构原单查询核实，不直接覆盖。回调入口不得由浏览器角色模拟调用。

### 6.5 单笔分账手动调整

“单笔”指某个收款方的一条业务应结或其一次付款安排；一笔可关联多条原支付执行行，保留所属业务与结算单位。权益与生活服务使用同一个调整入口，差异由各业务可调整范围及资金路线校验。运营在分账详情点击“调整”，服务端先生成影响预览，保存调整申请和原因，按策略取得新授权后生效。保留原规则计算结果、调整值与最终计划值，不能直接覆盖历史账。

外部订单同样可提交合同应计或账单更正申请，按相应目的审批；修改金额不覆盖外部实际支付／退款凭证。对外部付款时间或账户的更正只更新有证据的记录，需变更原渠道付款安排时转原渠道处理，本站不发送资金指令。资金型操作不可通过接口直调绕过此限制。

| 调整项 | 产品操作与生效规则 |
|---|---|
| 本次付款金额 | 可增加至该义务剩余可付额度，或减少并分次支付；未付余额继续保留应付，明确后续时间或暂缓原因；不能把少付自动当减免 |
| 应结总额 | 可提出调增／调减；以独立业务调整单记录合同、差错更正、费用承担等依据，产生平衡调整分录，不改原核销公式。调增须有批准且可用的资金，调减须有相应合同或双方确认依据 |
| 计划付款时间 | 选择具体日期时间、提前／延后或暂缓；保存原日期及新日期、原因、恢复条件。表示最早发起时间，不承诺银行到账时间 |
| 收款账户 | 选择同一合法受益人已经准入、支持该币种及支付合同的账户版本；新增账户先走账户审核。变更法律受益人须另走授权关系变更，不能仅改银行卡号 |
| 费用、抵扣、备注及附件 | 支持调整合同允许的费用／追偿抵扣项并联动重算净额，保留承担方和证据；纯备注更新不改变金额授权，修改费用必须重新授权 |

金额设计明确区分：original_payable、approved_adjustment、adjusted_entitlement、paid_amount、active_reserved、remaining_payable 和本次 planned_amount。退款／业务冲回对已付部分仍按原设计转为应收追偿，不能通过调减应付掩盖已发生付款。

共享义务层以 discharged_amount 记录历史清偿，分别展示 transferred_amount 与 merchant_released_amount；旧 paid_amount 若只表示转账成功，不能直接充当剩余应付的扣减总额。商户原款释放成功后剩余应付同步减少，重复回调和重新生成计划不能恢复这部分额度。

应结调增生成关联原义务、带独立来源的补差组件；调减只取消尚未清偿的授权额度，已清偿部分另建应收追偿。原义务及其分次计划共同锁额度：历史清偿（成功划转＋商户原款释放）＋活动支付占用＋生效及活动抵扣≤原批准额度＋已生效补差额度−已取消未清偿额度；各组件还分别校验自身额度。改计划或新增一期不能各自重新获得一份全额付款权；已退回资金按原设计新建关联义务，不清空原成功累计。

例如原商户应结 159.84 元，手动安排本次先付 150.00 元，账单仍显示应结 159.84、计划本次 150.00、剩余应付 9.84；后续 9.84 共用同一义务额度控制。若商户应结确需调增至 169.84 元，新增 10.00 元必须指定平台自有资金或获准承担来源；不能从其他用户未核销款补齐，也不能无记录压减推广佣金。原 B/Q/N 与调账结果分列，调整影响平台佣金或净留时同步生成相关调整分录和授权。

收款账户调整按 funding_mode 解释。机构代收模式可在已批准的同主体账户之间改选分账收款账户；商户原款模式保留原机构收款来源，只有机构支持原受控资金定向转移时，才能生成有原资金来源的账户转移动作，并与原账户释放互斥。机构不支持此能力时，仅允许其认可的结算银行卡变更并保存版本及证据；不能同时释放旧账户 S、再向新账户付一遍 S。原款已清偿后，不能通过修改账户重新生成原应付款。

| 当前状态 | 是否能调整及处理路径 |
|---|---|
| 草稿／规则评估中 | 保存新修订，按新内容评估 |
| 人工审批中 | 撤回或使旧审批实例失效，以新 revision 重新提交；旧审批按钮提交返回版本冲突 |
| 已自动／人工授权，尚未发送 | 原子暂停受影响的待发送任务、撤销旧授权、调整占用并创建新修订；重新授权后按新时间执行 |
| SUBMITTING／PROCESSING／UNKNOWN | 不允许原地改外部请求；调整诉求可登记为待处理，先查原单。只有机构确认未出金且旧单不可再执行后，才重新编排 |
| PARTIAL／SUCCEEDED | 成功行不改；未发送剩余部分可单独调整，成功部分通过补付、回退或应收追偿处理 |

编辑与发送使用同一版本条件和数据库状态切换竞争：编辑先赢则旧 worker 无权发送；worker 先进入 SUBMITTING 则编辑被阻断，即使网络尚未返回也不能按“未看到成功”重建付款。共享机构请求内一行发生变更，必须在请求未发送时废止整个旧报文并重编；其他未变更行可复用仍有效的业务授权，但不能让旧请求也继续发送。

时间检查同时覆盖合同可付时间、最晚应付日、机构分账／退款期限和资金可用性。提前不能越过本业务核销／履约确认、机构可分或合同限制；延后跨账期仍保留原业务期并在后期结转展示，不重复产生应付。超出合同范围必须先落实新的依据及所需审批，不通过填写任意时间绕开限制。暂缓须有责任人、复查时间和解除动作，到期提醒，不自动当作同意付款。

默认金额、账户及超出合同窗口的时间调整进入人工审批；在已批准授权范围内的时间安排可由配置规则自动放行。具体范围由 §6.6 的手动调整策略版本控制，规则校验、资金覆盖和在途保护不因自动结算而关闭。所有调整记录申请人、时间、前后值、原因、证据、授权路径、生效事件和关联外部单。

### 6.6 按商户等规则配置自动结算或审批后结算

结算策略与佣金计算规则分别版本化：前者回答“是否需要人审、谁审、何时执行”，后者回答“应结多少钱”。开户／账户资料、商业规则和自动策略本身的发布审批，不等于要求每笔正常付款都人工审批。

| 配置层 | 可配置内容 |
|---|---|
| 匹配条件 | biz_type=commerce/jiazheng、法律主体／商户、合同、收款方类型、城市／服务类型、商品、金额区间、累计额度、账户是否变更、是否手动调额、是否首笔付款及异常标签 |
| 执行模式 | AUTO：系统校验通过后到时自动执行；REVIEW：完成指定人工节点后到时执行；HOLD：暂停并登记原因 |
| 自动范围 | 单笔与同主体累计限额、允许的账户和时间范围、适用费用规则、例外转人工条件；缺项不解释为无限额 |
| 人工流程 | 按顺序配置“运营核实→财务审核→负责人审批”等节点，可只配置一节点；各节点选择岗位／指定人员、候选范围、任一通过或全部会签 |
| 超时与例外 | 催办时间、代理／转交范围、超时升级人、缺审批人时的兜底队列；超时、离职或无人处理均不得自动通过 |
| 生效管理 | 草稿、测试预览、发布复核、生效时间、版本、停用；影响历史单据时显示清单并重走授权，不能静默追溯 |

判定顺序为：资金及机构硬校验 → 冻结／风险／人工调整例外 → 明确优先级的商户／合同规则 → 分组规则 → 默认规则。同级重叠规则发布时拒绝或要求消除歧义；运行时遇到无法唯一匹配、缺配置或数据未知时转人工／阻断，不能默认自动付款。系统展示命中规则、未通过条件和实际审批路径。

示例仅展示配置方式，不替业务确定金额阈值：

- 商户甲的正常账期款、既有有效账户、无人工调额，且处于批准限额内 → AUTO。
- 商户乙的全部款项 → 财务一节点审核后付款。
- 任意商户发生调额或更换收款账户 → 按例外规则进入“运营核实→财务审核”，优先于商户 AUTO。
- 达到配置的大额／累计额度门槛 → 增加负责人节点；不得把同一义务拆成小额付款绕过门槛。

审批人由服务端按商户／组织范围和权限解析，记录当时名单；申请人、调额人不能审批自己的事项，需要多人会签时按配置校验不同实际人员，不能一人切换角色满足全部节点。审批通过、驳回、退回修改、撤回和受控转交均有独立事件；节点依赖未满足不能提前通过，旧版本回调不推进新实例。

自动模式记录 system_actor、policy_version、匹配输入、规则结果、限额占用及授权 hash，不伪造人工审批人。每日／账期累计限额在发送前原子占用，按法律主体汇总关联义务及分次付款，未知结果不释放，明确未付后才释放；授权过期、账户暂停、新增售后冻结或限额变化时暂停待发送任务并重新评估。

结算策略发布权限、单笔调整权限、人工节点审批权限、机构执行服务权限分离。配置自动策略不得成为操作者自行修改收款账户并绕过账户审批的通道。人工节点全部通过也不跳过发送前的资金、账户、版本、时限检查；审批完成晚于计划时间时，记录延误并在仍符合合同及机构条件的下一个可执行窗口处理。

同一商户可配置“生活服务正常订单 AUTO、权益订单 REVIEW”，也可发布明确覆盖两业务的主体累计额度规则。跨业务规则必须显式声明范围；不能因为商户 ID 相同就继承另一业务更宽松的自动条件。累计额度按规则指定的主体／业务范围合计，拆业务、改账户或分次付款不能绕过该范围的总限额。

策略条件和授权摘要同时包含 payment_mode、execution_scope 与 purpose。外部可配置自动生成账单、自动匹配满足证据政策的记录或人工复核差异；命中 AUTO 只完成对应账务动作，不能复用站内出金授权。

## 8. 账务、退款、追回与赔付

§8.1—8.4 的机构资金执行针对站内及已准入来源；外部消费者交易与外部合同佣金按 §8.5 单独列账，均进入统一对账单，但不套用站内消费者资金负债及自动退款流程。

### 8.1 业务子账

本表为业务清分子账示意，正式财务总账科目及代理人收入确认由财务映射。所有分录在 settlement 域追加写入，每组借贷相等、每个业务事件唯一；不能借贷平衡就认为资金真实存在。

业务子账可追踪多主体，但每条资金记录标明法律主体、资金所有权及镜像性质；跨法律主体划拨时分别生成各自主体平衡的收付及往来镜像，不在单一法人总账直接借另一法人的现金。下表中的“机构待清分资金”是清分控制记录，不主张全部属于平台自有资产。

| 事件 | 借方 | 贷方 | 触发凭证 |
|---|---|---|---|
| 权益用户支付成功 | 机构待清分资金 A | 权益待发券负债 A | 可信支付成功事件 |
| 发券完成 | 待发券负债 A | 按券未核销负债及会员专项负债 A | 幂等发券事件；不再重复记收款 |
| 生活服务支付成功 | 该订单机构受控资金 A | 生活服务待履约负债 A | 被 guard 接受的可信支付事实；不经过发券分录 |
| 权益比例核销 | 权益未核销负债 A | 商户应付 S、推广应付 Q、平台业务净留 N | 有效核销与计算快照 |
| 生活服务比例确认 | 生活服务待履约负债 A | 商户应付 S、推广应付 Q、平台业务净留 N | 服务有效确认与该业务计算快照 |
| 商户分账成功 | 商户应付 S | 机构待清分资金 S | 商户分账行成功 |
| 商户原款释放成功 | 商户应付 S | 商户原款受控资金 S | MERCHANT_RELEASE 的机构证据；只结清一次，不另记向商户转账 |
| 平台佣金入账 | 平台机构资金 B | 机构待清分资金 B | B 的真实入账或同账户归属转换 |
| 推广代发完成 | 推广应付 Q | 平台机构资金／代发资金 Q | 净款、税费、服务费分别有完成依据 |
| 未核销退款受理 | 对应未核销负债 R | 退款应付 R | 冻结券及已批准政策；资金仍未出账 |
| 用户退款成功 | 退款应付 R | 机构待清分资金或退款出资账户 R | 原支付退款成功凭证 |

手续费单独建费用及承担方分录。若收单手续费从原款直接扣除，必须同时记录净实收与费用，确保给商户、推广及退款的承诺额有资金覆盖；不能以“毛额 999 元”假定机构余额永远是 999 元。

上表生活服务分录适用于已确认受控来源。MERCHANT_ALREADY_SETTLED 的历史款须按实际既付与佣金应收导入，不重记“待清分资产 A＋待付商户 S”。科目同时标记 biz_type、主体和资金来源，跨业务余额不能互相填补。

推荐首期不改变商户 S 和推广税前 Q 的计算，支付手续费及代发平台承担部分从平台净留／自有费用账户列支，仍需业务审批。若合同由商户或推广承担，锁定各自应扣项；任何不足从已到账平台自有资金补足并留来源，不能侵占其他用户未核销资金。

### 8.2 推广代发和税费

Q 是合同佣金口径，页面分开显示：税前佣金、代扣税、受益人承担服务费、实付净额。使用财税及代发产品确认的 tax_profile，不将需求测算中的“20%”直接写为统一税率。

若税前 99.90 元的测试单收到机构计算结果“代扣 19.98 元、服务费 0、净付 79.92”，三项应合计 99.90。这只是接口勾稽测试数据，实际税额依机构与适用规则返回。

平台先把资金交给代发机构，并不代表个人已经到账：该步只转为代发在途资金；逐人净款成功及代扣义务承接／缴付证据按合同分别记账。失败或部分成功保留剩余应付，不能整批清零。

平台仍负缴付责任时，已确认代扣但未缴部分应从推广应付转为税款应付，缴付成功后才结清；若合格代发机构依法依约承接义务，需保存承接凭证及后续税务结果。净款已付不自动表示税款或服务费已结清。

推广员自助提现只消费已到可结算时点、无争议且有机构资金支持的 Q 来源。自动双周代发与主动提现共用同一来源占用，单条来源只执行一次；提现按钮不创造新应付或第二次付款。

### 8.3 退款和误核销

| 时点 | 处理方式 |
|---|---|
| 未核销、未分账 | 锁券和原支付退款额度，冻结券及预约；退款计划关联原 payment_refund；成功后才关闭负债及标已退款 |
| 已核销、尚未发送分账 | 双人审核撤销／售后；原计算全额或按政策冲回；作废未执行计划并释放对应占用，批次重新审批 |
| 分账处理中／UNKNOWN | 冻结相关后续支付与退款编排，查原分账各行；不得按“尚未看到成功”当作未付款 |
| 已成功分账 | 按原成功分账行发回退；成功回退进入原可退款来源，再执行原路退款 |
| 回退不足或个人代发不可退 | 留存应收追偿；按批准的自有资金垫付规则先解决退款／赔付，追回单继续开放 |
| 部分退款 | 保存退款分配及每个原分账行累计回退；不得超过该原行净已付或原支付可退余额 |

退款已转为退款应付后，若用户撤回或审批撤销，必须确认原退款从未成功、无在途且机构不可再执行，再反向转回对应负债；券是否恢复还须检查有效期。退款失败但仍须履约退款义务的，继续保留退款应付及券冻结，不能当作取消。

支付成功但永久发券失败可按 order_id + funding_source_id 建退款，不要求已存在 coupon_id；该类 RefundAllocation 的券引用为空、订单引用必填。接受终止履约和创建退款计划在同一 guard 保护下完成，阻止晚到的发券重试；已部分发券时逐单位判断，未发部分与已发未用部分分别关联。

分账回退是资金回到退款出资方，消费者退款是钱回到原付款人，二者必须有各自成功凭证。业务冲回也不代表已追回实款。

生活服务原商户收款模式下，S 是原款释放，可能没有“S 的原分账单号”。退款须从该商户原支付来源的实际可退款资金出款；B 则按真实平台分账行发回退。商户已提走 S 时，使用有授权的商户回补／扣款能力或批准自有资金垫付，不能伪造 S 的 splitReturn。若只退服务部分，按服务 RefundPolicy 与原分配拆分回退责任，不机械退全单。

累计约束分别锁定：

~~~text
原支付成功退款 + 有效在途退款 <= 原支付实付可退上限
原分账行成功回退 + 有效在途回退 <= 原分账行成功金额
券累计退款 <= RefundPolicy 冻结的券可退金额
补贴退款去补贴来源，不增加用户可退现金
~~~

误核销的已付款部分冲回不能只借记已清零的商户应付：未付部分冲销应付，已付部分转为该收款方应收追偿；平台已入账份额按原计算反向处理。原券恢复可用前确认机构资金已回补，或已有批准且到账的垫付来源，避免同券再次核销形成无资金支持的第二次应付。

例：A 券的 159.84 商户款和 19.98 推广款均已付，19.98 平台净留已确认；批准全额退款 199.80 后，业务子账借“商户应收追偿 159.84、推广应收追偿 19.98、原平台净留冲减 19.98”，贷“退款应付 199.80”。真实回收借对应机构资金、贷原应收；退款成功借退款应付、贷退款出资账户。平台 B 的回退只调整资金位置，不再新增另一份 39.96 的追偿或重复冲收入。上述例子不含税费，含税费时按原拆分组件处理。

两段路线中，如果推广 Q 已付：先记录 Q 的追偿责任；按机构支持程度回收至平台佣金账户，再处理原 B 回退。无法同步追回时，从平台自有资金补足 B 所需回退额度并记应收；不能先把 B 全额回退后假定推广款仍在账户。

部分逆向采用原快照的累计目标法：本次冲回额=按累计批准退回比例计算的目标冲回额−此前累计已冲回额，最终全退时补齐到原组件金额，避免每次单独 floor 造成永久尾差。消费者退款政策与商户／佣金冲回政策分开保存；不能自动假定消费者退多少，商户和推广就必须同比例承担。已关账期保持原账单，新增当期负调整关联原核销与原期。

追推广佣金需拆“已收净款、税额、服务费”的承担及可退性；机构退税／费用返还另记事项，不能同时向推广员追毛佣金和净款两份，也不能把用户退款当作退税凭证。

重复、乱序和迟到成功逐行落事件；“已成功”不可被失败通知覆盖。原失败后出现可信成功，冻结关联替代计划并查原单，不继续付款。

已使用自有资金退款／赔付后收到迟到回退，先唯一关联原垫付应收并回补自有账户，不再次发起用户退款。同一机构回收流水只能核销一份对应追偿分配。

分账／代发成功之后的银行退汇以独立 RETURNED 补偿事件记录，保留原成功历史；确认资金退回后，按合同新建关联的待付义务及批准计划，不释放原执行组件的历史付款额度。推广重付只处理尚欠净款，原已缴税及已收服务费不自动重扣；商户银行结算失败不重发上游分账 S。

### 8.4 赔付与追偿

已核销但履约失败可按批准规则使用独立赔付账户。流程为“申请→复核→出金待执行→机构处理中→成功／失败／未知”；批准动作只产生付款授权，绝不直接写 paid。

每笔赔付绑定用户损失、责任商户、预算、原支付、售后案件和应收代偿／保证金抵扣依据。原路退款、额外赔付、追回相互关联；累计补偿额度受案件决议约束，避免同一损失被退款和赔付各全额支付一次。

追偿状态为 OPEN／PARTIALLY_RECOVERED／RECOVERED／WRITTEN_OFF。回收金额来自真实回退、银行到账或合同允许的有效应付款抵扣；仅余额归零或另行核销审批后关闭。坏账核销不是已收回。

下期抵扣仅限同一债务法律主体、币种及有权抵扣的合同范围。被抵扣的新账款对应资金留在何处、如何回补原垫付账户，也必须产生机构资金计划或经核验的账户归属记录；本地减少付款金额不等于垫付资金已经回收。

同主体跨权益与生活服务的抵扣，仍须有覆盖两业务的明确合同授权及资金来源安排；仅账单汇总或主体映射成功不产生抵扣权。

抵扣分为 OFFSET_RESERVED 和 OFFSET_SETTLED：提交计划只占用拟抵扣额度；合同确认的债务抵销生效和机构资金归属证据齐备才登记实际回收。在途、失败或计划取消时按实际生效情况保留或释放占用，不能在请求发送前直接关闭追偿。抵扣内容属于批准摘要，执行人不能临时调整。

### 8.5 外部交易、佣金应收与退款记录

外部消费者向商户付款只是外部交易证据，在交易辅助记录中列 gross_paid、successful_refund、external_net_receipt；不借记本站机构资金、不贷记本站消费者负债、不生成商户 S 应付。合同应计单独记录 creditor_party_id、debtor_party_id、obligation_direction、component 和批准规则，按法律主体与实际债务分别汇总。

满足已批准合同的支付证据、履约和计费条件后，平台佣金可形成“借：商户佣金应收；贷：佣金收入／待确认科目”的平衡分录，具体科目和确认时点由已批准的会计政策决定；尚未满足条件时仅展示预计／待确认金额。平台是否欠渠道推广款、费用由谁承担分别按独立合同确认，不从外部商户净额推导平台应付，也不套用权益推广比例。

外部佣金实际汇入平台后，以平台收款账户真实入账流水和逐组件分配确认清偿，借对应收款资产、贷商户佣金应收；同一到账已被公共收款账本登记时只引用既有资金事实并完成应收认领，不能再确认一次现金或佣金收入。外部渠道称“佣金已结”但缺平台到账／有效债务抵销证据时，仍显示报送待核验。未分配的批量收款保留待认领，不重复销减多份应收。

外部消费者退款关联真实原外部支付和退款号，核验累计成功退款不超原款；只取消订单或商户声明退款中不登记退款成功。退款事实与佣金冲回分别处理：消费者确已收到退款，即使佣金承担有争议，也照实记录外部退款并将佣金列为待处理。批准冲回先减少尚未清偿应收；已收部分需返还时另列平台对商户的退款／抵扣义务，记录真实返还或生效抵销证据，不能把原佣金实收抹去。

本站不为外部消费者退款创建 payment_refunds、splitReturn 或资金 Outbox；外部原渠道退款及佣金结付事实通过回传、查询或凭证导入更新。已生效抵扣需合同依据及双方债权明细，跨支付渠道的应收与站内应付不能因同一商户就自动相抵。

示例仅用于设计验算：外部商户收款 200.00 元，已批准平台佣金为核验实付的 10%，无推广、税费，履约条件满足后，账单列“外部实收 200.00、平台佣金应收 20.00、商户经济净额 180.00、本站应付商户不适用”。平台另核验收到佣金 12.00，应收剩余 8.00；随后原渠道成功退给消费者 50.00，且合同明确该情形同比例退佣，累计应计变为 15.00、本期冲回 5.00，应收余款为 3.00。用户退款 50.00 与佣金冲回 5.00 不合并成 55.00 用户退款；全部动作均不产生本站对商户 180.00 的付款。

已退款、已结付记录即使随后发生差错也保留原事实版本；更正通过关联原事件的撤销／修订证据和差额分录完成。历史证据不足的存量订单先出账为待核验，不按当前费率自动追算。

## 9. 四方对账与守恒

每天采集支付／退款账单、分账／回退明细、代发逐人结果及费用／银行结算凭证。原文件按版本、hash、账单日留存；重传去重，更正账单保留旧版并追加调整。

外部渠道也按约定频率接收商家报送、交易／退款／结算账单或人工凭证，并记录截至时间与覆盖范围。外部事实通过其原渠道证据核对，不要求伪造本站 execution_order 才能出账或完成核对。

对账四层：订单与核销／服务履约事实 → 业务子账 → 执行指令及回执 → 机构原始账单。不能继续用本地 provider_requests 表同时充当执行结果和“外部账单”。

| 层次 | 必须展示 |

| 抬头 | 账单编号、版本、受益人／收款法律主体、币种、合同、账期、统计截止时间、生成时间；收款账户掩码及账户版本 |

| 逐笔 | biz_type、脱敏原订单／结算单位、履约确认引用（权益附券／核销，服务附服务单）、规则应结、调账额、调整后应结、本次计划额、计划付款时间、实际入账时间、划转或原款释放方式及机构流水 |
| 金额细项 | 手续费承担、税前／税额／服务费／净额、退款／回退、追偿及退汇；调整原因及对收款方应公开的依据 |
| 核对状态 | 业务应结已确认、已发指令、机构账户入账、银行结算／到账分别显示；已核对或差异待处理及统计范围 |

应付型账单的勾稽为：

~~~text
期末未结 = 期初未结 + 本期新增应付 + 生效调增
         − 生效调减 − 生效抵扣 − 本期已清偿额 + 退汇恢复应付
~~~

待审、暂缓、计划待付和在途款仍属于未结中的子状态，不再额外扣减；各子状态按同一金额切片互斥统计。调减只减少仍未清偿部分，已付后的业务撤销转为追偿应收，在账单另列；不能重复减应付。推广“已清偿额”按合同记录净款支付及有效税费承担／转付，毛额与净额分栏，不能把 79.92 元净到账显示为 99.90 元银行卡到账。平台调拨型账单另用账户期初余额＋收入−支出＝期末余额，不机械套用应付公式。

商户“本期已清偿额”包括本期成功划转及机构确认的原款释放，两类分栏并保留各自证据。原款释放不展示为新增转账，也不等同银行卡到账；撤销本地预占不计入已清偿额。

例：商户期初未结 0、本期新增应付 159.84、无调账抵扣、本期成功支付 150.00，则期末未结 9.84。界面和下载文件必须得到同一结果；不能因本次执行单 150.00 已成功而把原义务标全额结清。

账单出具状态与核对状态分开：publication_status=DRAFT/ISSUED/SUPERSEDED，recon_status=PENDING/MATCHED/DIFFERENCE，coverage_status=COMPLETE/PARTIAL/NOT_RECEIVED。待核对账单可查看、下载，但明确标明截至时间和未核对项；“已出账”不等于所有款项到账。覆盖状态按渠道、商户账号、事实类型及日期范围记录，无完整性证据不自动升级 COMPLETE。

每份已出账单冻结 version、as_of、来源事件集合及汇总。后续付款、调整、退汇或机构更正生成补充版／新版本并关联被替代版本，旧版保留，不能覆盖已下载的历史内容。已关账期的业务调整入实际调整期并引用原期；新版本只是更新截至该时点的结算进度，不把后期交易倒记到原期。

区分“账期末余额”和“截至当前的原期款项结清进度”：上式按各事件实际入账期间计算，下一期期初承接上期期末；后期付款列在后期账单，并在原期明细的结清进度中引用，不回写原期已冻结的期末余额。下载文件分别标注 period_end 与 as_of，避免同名“期末未结”随下载日变化。

例如某账期应付 100 元、期内未付，下一账期实付 100 元：原期账单仍列“期末未结 100”，补充进度另列“期后清偿 100、截至本次统计未结 0”；下一期列“期初未结 100、本期已清偿 100、期末未结 0”。两期流水仅计一次实际支付。

### 9.3 下载、导出与异议

提供 CSV／XLSX 明细、PDF 汇总及明细对账单；按数据量异步生成。导出请求锁定 statement_id + version + as_of + 导出范围，页面和各格式消费同一账单快照，不用导出时的实时 SQL 重算一份金额。

导出链路为“申请→排队→生成→可下载／失败／过期”，返回任务号；相同版本和范围可复用文件。文件带账单编号、版本、币种、截止时间、筛选条件和汇总，提供生成状态及失败重试。CSV／XLSX 的名称、备注等文本按纯文本输出，账户及用户信息遵循账单字段白名单。

生成任务和每次下载均校验当前主体权限；受控下载地址短期有效，撤销授权或切换主体后不得凭旧链接继续下载。文件保存在受控存储，访问经鉴权网关，不能把完整机构原始账单直接提供给某个收款方；下载审计记录操作者、主体、版本、文件 hash、时间和结果。

收款方可针对整单或具体明细发起异议，填写原因和附件并查看处理进度。仅发起异议不自动冲账；经规则或人工确认争议后冻结相应未付金额，已付部分进入追偿／退款流程。异议关闭需要处理结论及证据，金额变化通过调整单生效，并在后续版本体现；已付款、申诉中、已解决三类事实分别保留。

### 9.4 外部小程序账单的出具规则与展示

外部订单与站内订单使用相同的账单中心、版本、下载和异议入口；外部账单自动按 statement_policy 出具，不要求商户先申请、不等待原渠道结算完毕、不依赖本站分账开关。账单默认范围为本站引流及已有合法业务关联的订单；整店渠道文件中的其他来源订单不得混入本项目交易总额或向无权人员泄露。

出账任务按主体、币种、合同／出账策略、期间及渠道范围建立幂等键，周期到达后生成 ISSUED 版本。没有合同约定出账时间时，默认次月 1 日北京时间 08:00 出上个自然月账单，运行失败可按同一幂等键恢复；这是可配置出账时间，不代表付款日。期中支持截至当前的预览与导出，明确标“期中对账单”。同一截止点和源事件版本重复生成返回原账单，有新增证据再生成新版本；生成失败不清除已出版本。

每期候选集合包括：期内新建订单、期内支付／履约／退款／清偿或调整事件、期初未结合同义务，以及以前期间尚待核验的订单。订单覆盖清单按 business_context_id 唯一，交易明细按规范事件唯一；同一订单本期有多种事件可列多行，但订单数只计一次。待支付跳转记录列在订单覆盖附表，不计作已成交；无交易且证据覆盖完整时才标“本期零交易”。

| 外部账单栏目 | 显示口径 |
|---|---|
| 订单覆盖 | 平台 order_ref、商家 vendor_oid、商品／服务、商户、业务及支付渠道；已匹配、待匹配、支付未确认、资料待补数量 |
| 外部消费者交易 | 已核验实付、已核验退款、外部交易净额；商家报送待核验金额单列，金额未知显示“待补”，并列未知金额订单数 |
| 合同应计 | 有效规则版本、计费基数、商户经济净额、平台／渠道佣金及各自债务方向；无有效费率时显示“待确认／未计费”，不自动套用 10% |
| 外部结算及平台实收 | 渠道结算毛额／费用／净额、结算对象、实际平台佣金清偿、剩余应收及原凭证；没有银行证据时不显示银行卡已到账 |
| 差异与完整性 | 待证据、金额差异、漏单、重复、退款不匹配、归属冲突；覆盖范围、最后接收时间、缺失文件／日期与核验来源 |
| 版本和时间 | period_start/end、as_of、source_cutoff、occurred_at、received_at、verified_at、posted_at、原期及更正引用；历史版可查 |

所有数值都带口径：已确认与待核验分别小计，未知项只计数量，不能以空值参与求和后将结果标为“全部实收”。待核验行出现已知商品报价时单列“报价”，不放进实付列。机构应结和银行卡到账、商家消费者收款和平台佣金收款分别展示，不叠加同一资金多次流转。

外部证据发生时间可信时按对应交易日期展示，合同应计及清偿按实际入账期记账；缺发生时间时展示“发生时间待补”，暂列接收期待核验附表，并明确历史 gr_orders 的 paid_at 可能是回传接收时刻。补齐原发生日不追写已关账分录：在当前期补记／调账并标原交易期，原期补充版只更新核验和期后进度，原期末余额保持冻结。期间仍开放时可按政策产生可追溯修订，不能同时在原期与本期各记整笔金额。

商户“确认账单”记录对该版本的接受或异议，确认动作不等于资金已付、证据已核验或放弃后续差异权利。查看下载不要求先确认；更正后确认对象换成新版本，原确认记录保留。待核验、存在差异、部分资料缺失的版本均可查看和下载 CSV/XLSX/PDF，文件与页面保留相同标签、金额口径及完整性说明。

验算示例：某商户有一笔已核验外部实付 200.00、一笔仅商家报送 100.00、一笔完成但金额未知的订单。账单列已核验 200.00、报送待核验 100.00、未知金额 1 单，不能显示“已核验 300.00”。后两笔证据补齐后生成新版本，同一规范交易不重复累加；若无完整的期间覆盖证明，整体仍保留数据未齐状态。

## 11. 实施拆分与验收

### 11.1 按交付结果推进

| 批次 | 实施内容 | 退出证据 |
|---|---|---|
| A：规则及机构契约 | 两业务实际收款路径、party 绑定、各自费率／履约确认／退款政策、账期与自动／人工策略、ACN 契约 | 生活服务商户原款受控能力单独验证，不以站内支付开通代替分账准入 |
| B：共享底座与兼容迁移 | 抽取 server/settlement、权益兼容入口、泛化表与事件、业务适配器、调整／策略／授权、多对多执行单 | 隔离库迁移及权益回归；无双写、假券或新旧引擎重复支付 |
| B2：外部交易正常出账 | gr_orders 映射、持久外部事实、导入核验、合同应计、独立账单任务、页面下载及历史版本 | 未接本站收银台也能周期出账；缺证据不漏单，外部账单与本站资金任务严格隔离 |
| C：两业务收款与分账沙箱 | 权益核销、生活服务验收事件、收款唯一入账、商户划转／原款释放、平台 B、原单查询 | 两业务各自取得机构沙箱请求、回执和原始账单；200 元服务例防商户重复收款 |
| D：逆向与推广及收款方账单 | 多次部分退款、splitReturn、个人代发、赔付追偿、银行结算、全部收款方账单／导出／异议 | 正反向逐笔对平；下载同快照、跨主体隔离、历史版本可追溯 |
| E：真实小额闭环 | 各业务获准商品、真实主体、小范围销售；分别覆盖完整合同账期 | 权益核销及服务验收各完成资金正逆链；单一业务成功不代表另一业务已验收 |

不承诺未经团队估算的工期；每批次按证据放行。没有真实代发能力时，不发布承诺可提现的推广计划；没有完整退款能力时，不开启对应权益销售。

B2 在共享底座就绪后独立交付，外部对账出账不等待 C—E 的站内机构资金联调。外部数据接口未完成时，先用已有合法订单生成待核验账单，并提供受控导入／补证；不能以等待自动接口为由不出账。完成 B2 的证据必须包含一份外部正式账单及各格式导出、补证后新版本和真实权限隔离记录。

共享化迁移分三步：先为既有权益记录回填 biz_type=commerce、业务上下文和单位映射，保留原金额／事件／指令号；再将旧入口转发共享核心并验证只写一次；最后按商户及业务白名单接入生活服务。历史权益款不作为新事件重记，不让两版 worker 同时消费同一队列。生活服务旧单走 §4.4 的独立核验导入。只读影子计算可用于比对，禁止影子路径发钱。

外部历史迁移从 gr_orders 的原 payment_mode、业务来源和商户归属建立只读候选事实；缺原配置的先按现有记录和证据核验，不能用当前商户支付模式覆盖。既有状态／金额作为 MERCHANT_REPORTED 或历史来源记录，不假设机构已核验。迁移以源表及主键幂等，站内订单的 gr_orders 展示投影只建别名映射，不新增外部交易。演示数据不进入正式账单；历史同单多投影、缺主体或发生时间未知均可回溯至待核验清单。

已有 004/005 迁移只读，新增版本负责 nullable 外键调整、非空通用键、索引及校验；通过隔离库演练后再做可恢复迁移。上线开关按 biz_type＋商户＋funding_mode 独立设置，暂停生活服务分账不影响权益的存量查单和退款。
