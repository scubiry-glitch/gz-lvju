# 旅居民宿预订业务产品说明书

版本：基于当前代码现状整理  
范围：旅居找房、民宿/旅居预订、商家后台、平台后台、房源开放接口接入  
更新时间：2026-09

## 1. 产品概述

本业务是一套围绕“旅居 / 民宿房源预订”的业务闭环系统，覆盖以下能力：

- C 端旅居找房、房源详情、日历选房、下单、支付、订单查询、取消
- 商家后台房源上下架、房态与夜价维护、交易方式配置、订单确认/拒单
- 平台后台商家入驻受理、房源项目配置、评级复核
- 商家开放平台 HMAC API，用于外部 PMS/OMS/中台系统直连接入房源、户型、图片、房态与订单履约

当前代码口径下，系统不仅支持单间单晚预订，还支持：

- 多间库存
- 房型维度免费取消政策
- 房源维度交易方式配置
- 房源维度最短连住与保险能力
- 商家 Webhook 回流通知

## 2. 业务目标

本业务的核心目标是把“房源供给接入”与“C 端成交履约”打通，形成统一的房源交易中台。

具体目标包括：

- 让外部商家可通过 API 快速接入房源
- 让平台可对房源进行审核、评级、上架管控
- 让 C 端基于真实库存、真实价格完成预订
- 让商家在 B 端或开放接口侧完成确认、拒单、房态维护
- 让全链路使用同一套 MySQL 数据口径，避免多套系统数据分裂

## 3. 角色与职责

| 角色 | 说明 | 主要能力 |
| --- | --- | --- |
| C 端用户 | 旅居 / 民宿消费者 | 找房、选房、下单、支付、查单、取消 |
| 商家 | 房源供给方 | 接入房源、维护库存与价格、确认或取消订单 |
| 平台运营 | 平台管理方 | 审核商家、配置项目、复核评级、代管房源 |
| 外部商家系统 | PMS / OMS / 自有中台 | 通过 HMAC API 接入房源与订单履约 |

## 4. 技术架构

### 4.1 总体形态

- C 端：静态多页 HTML + CSS + 原生 JavaScript
- 商家后台 / 平台后台：静态多页控制台 + 原生 JavaScript
- 服务端：Node.js 单体服务，主入口为 `app.js`
- 数据库：MySQL
- 移动容器：Capacitor，Android WebView 直接加载远程站点

### 4.2 关键模块

- `app.js`：HTTP 服务主入口、公开接口、商家后台接口、平台后台接口、订单与库存主流程
- `vendor_api.cjs`：商家 HMAC 开放接口
- `stay_config.cjs`：房态、夜价、多间库存、取消政策、交易能力单一口径
- `auth_center.cjs`：账号、权限、会话体系
- `rating_config.cjs`：房源评级维度与校验
- `vendor_rate.cjs`：商家费率口径

### 4.3 架构结论

这是一个典型的“业务型 MPA + Node API + MySQL”架构，不是 React/Vue SPA，也不是前后端完全分离的前端工程。  
页面跳转以静态页为主，业务能力收敛在服务端接口上。

## 5. 核心数据模型

### 5.1 房源主数据

- `projects`：房源项目主表
- `units`：房型表
- `photos`：项目 / 房型图片表
- `cities`：城市
- `districts`：行政区

### 5.2 交易与库存

- `booking_contacts`：常用联系人
- `booking_orders`：预订订单
- `stay_calendar`：房态日历差异表

### 5.3 商家与入驻

- `jz_vendors`：商家主体、HMAC 密钥、Webhook、费率等
- `vendor_onboarding`：商家入驻申请单

### 5.4 当前库存口径

系统已升级为多间库存模型：

- `units.total_qty`：房型总间数
- `stay_calendar.qty`：某晚放出间数覆盖
- `stay_calendar.booked_qty`：某晚已订间数
- `booked`：派生态，不再作为主存储状态依赖

计算口径：

```text
某晚剩余可订 = (qty 或 total_qty) - booked_qty
remaining <= 0 => 前端 / 查询结果显示为 booked
```

### 9.4 上架前置条件

房源上架前必须满足：

- 商家状态为 `active`
- 商家审核状态为 `approved`
- 房源 `rating_status='passed'`
- 已设置 `price_from`
- 至少 1 个户型
- 至少 8 张图片
- 已配置封面图

### 9.5 开放接口与后台的关系

开放接口不是另一套独立系统，而是与后台页面共用同一套表与同一套业务规则：

- 开放接口写入 `projects / units / photos / stay_calendar / booking_orders`
- 商家后台也写同一批表
- C 端直接消费同一套房源与库存数据

即：

```text
开放接口 = 机器接入入口
商家后台 = 人工运营入口
两者最终落到同一套交易模型
```

## 10. 订单与库存状态流转

### 10.1 房源状态

- `draft`：草稿
- `offline`：下架
- `online`：上架

| 状态 | 含义 | 进入方式 | 退出方式 |
| --- | --- | --- | --- |
| `draft` | 草稿，C 端不可见 | 新建房源默认进入 | 可改为 `offline` / `online` |
| `offline` | 下架，C 端不可见 | 手动下架 | 可重新改为 `online` / `draft` |
| `online` | 上架，C 端可见 | 满足上架前置条件后上架 | 可改为 `offline` / `draft` |

### 10.2 评级状态

- `draft`
- `pending`
- `passed`
- `rejected`

| 状态 | 含义 | 进入方式 | 退出方式 |
| --- | --- | --- | --- |
| `draft` | 未提审 | 新建默认 | 提交评级后进入 `pending` |
| `pending` | 平台复核中 | 商家或平台提交评级 | 平台复核后进入 `passed` / `rejected` |
| `passed` | 已通过 | 平台审核通过 | 房源内容变更后仍可继续保持；也可再次发起新一轮提审 |
| `rejected` | 已驳回 | 平台审核驳回 | 商家修改后重新提审进入 `pending` |

### 10.3 订单状态

- `pending`：待确认
- `confirmed`：已确认
- `cancelled`：已取消

| 状态 | 含义 | 进入方式 | 退出方式 |
| --- | --- | --- | --- |
| `pending` | 已创建，待商家处理 | 用户下单 | 商家确认后 `confirmed`，用户/商家取消后 `cancelled` |
| `confirmed` | 商家已确认 | 商家确认订单 | 当前实现下为稳定态 |
| `cancelled` | 已取消 | 用户取消、商家拒单、支付超时 | 当前实现下为终态 |

### 10.4 支付状态

- `null`：无需线上支付
- `unpaid`：待支付
- `paid`：已支付
- `expired`：支付超时
- `refunded`：已退款

| 状态 | 含义 | 适用场景 |
| --- | --- | --- |
| `null` | 不走线上支付 | 在线预订 / 线下收款 |
| `unpaid` | 待支付 | 在线支付单刚创建 |
| `paid` | 已支付 | 用户完成支付 |
| `expired` | 已超时 | 待支付单超时关闭 |
| `refunded` | 已退款 | 已支付订单被取消 |

### 10.5 房态状态

数据库存储状态以 `stay_calendar.status` 为准：

- `open`：开放
- `blocked`：关房

查询展示态还会派生出：

- `booked`：剩余间数为 0
- `past`：历史日期

| 状态 | 类型 | 含义 |
| --- | --- | --- |
| `open` | 存储态 | 可订或仍有剩余间数 |
| `blocked` | 存储态 | 商家关房，不可订 |
| `booked` | 派生态 | `remaining <= 0`，对外显示已订满 |
| `past` | 派生态 | 历史日期，不可订 |

### 10.6 状态机

#### 房源状态机

```text
draft <-> offline <-> online
  ^                 |
  +-----------------+
```

说明：

- 新建房源默认进入 `draft`
- `online` 必须满足商家审核通过、评级通过、价格 / 户型 / 图片齐全等前置条件

#### 评级状态机

```text
draft -> pending -> passed
   \        |
    \       v
     +-> rejected

rejected -> pending
passed   -> pending   （重新发起提审时）
```

说明：

- `pending` 表示进入平台复核队列
- `rejected` 后允许商家修改再重新提审

#### 订单状态机

```text
pending -> confirmed
pending -> cancelled
```

补充：

- `cancelled` 可由用户取消、商家拒单、支付超时触发
- `confirmed` 前若为在线支付单，必须先满足 `pay_status=paid`

#### 支付状态机

```text
null      （无需线上支付）

unpaid -> paid
unpaid -> expired
paid   -> refunded
```

说明：

- 只有在线支付单才会经历 `unpaid -> paid`
- 超时关闭会进入 `expired`
- 已支付订单如被取消，进入 `refunded`

#### 房态状态机

```text
open <-> blocked
open -> booked   （派生显示态：remaining<=0）
booked -> open   （释放库存后重新可订）
past             （历史日期派生态）
```

说明：

- `booked` 并非当前主存储态，而是根据 `qty / total_qty / booked_qty` 计算出来的展示结果
- 商家操作的是 `open / blocked`

### 10.7 交易流转

#### 在线预订模式

```text
用户下单
  -> booking_orders.status = pending
  -> pay_status = null
  -> 商家确认
  -> status = confirmed
```

#### 在线支付模式

```text
用户下单
  -> status = pending
  -> pay_status = unpaid
  -> 用户支付
  -> pay_status = paid
  -> 商家确认
  -> status = confirmed
```

### 10.8 库存占用与释放

下单时：

- 创建订单
- 对订单区间内的 `stay_calendar.booked_qty` 做递增

取消或拒单时：

- 对 `booked_qty` 做递减
- 纯占用行可删除
- 商家配置过的 `price_night / qty / blocked` 差异行继续保留

## 11. 关键业务规则

### 11.1 交易方式规则

交易能力按房源配置，而不是按频道写死：

- `online_booking`
- `online_payment`

至少需要开启一项，否则不可下单。

### 11.2 最短连住规则

- `rental` 默认最短连住 15 晚
- `minsu` 也受项目最短连住口径控制
- 商家可在 `projects.ext.min_stay_nights` 覆盖

### 11.3 免费取消规则

取消政策存于 `units.ext.cancel_policy`：

- 房型级配置
- 未启用则默认不可自助取消
- 客户取消接口受窗口限制
- 商家取消 / 拒单不受客户免费取消窗口限制

### 11.4 多间库存规则

- 房型支持 `total_qty`
- 某晚支持 `qty` 覆盖
- 下单时校验 `remaining >= rooms`
- 调低 `total_qty` 或 `qty` 时不得小于已订间数

### 11.5 查单安全规则

匿名查单必须使用：

- `order_no`
- `contact_phone`

禁止通过 URL 旁路传手机号查单。

## 12. 平台对商家的回流通知

平台支持向商家回推预订事件，签名算法与开放接口一致。

事件包括：

- `booking.created`
- `booking.paid`
- `booking.cancelled`

推送方式：

- 商家在 `jz_vendors.webhook_url` 配置接收地址
- 平台带 `timestamp + sign` 推送
- 失败重试 3 次
- 若仍失败，商家可通过 `bookings/list` 拉单兜底

当前旅居民宿预订业务已经形成了完整的“供给接入 + 平台审核 + C 端成交 + 商家履约”闭环。

从架构上看，本系统的核心价值不只是一个 C 端订房页面，而是一套统一的数据与交易中台：
